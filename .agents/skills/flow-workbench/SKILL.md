# 业务流程绘制与评审

在用户指定的现有需求主题中维护原生流程数据。日常读取、修改与保存默认使用流程 CLI，浏览器用于需要时的最终画布核验。目标是让读者仅沿画布就能理解“谁在什么条件下做什么、之后去哪里、何时才算结束”，而不是依靠聊天补充流程语义。

## 技能选择与规范归属

- 在需求平台画图、改图或评审原图时，使用本技能维护原生流程和节点说明。
- 需要独立 HTML 或 SVG 时，沿用用户指定的导出工具。若以工作台现有流程为来源，先读取最新已确认语义，再交给 `archify` 处理布局、渲染、导出与产物验证；导出不自动修改工作台原图。
- 工作台的详细绘图方法、业务语义、父子承接、异步来源、异常恢复、评审规则和案例集中维护在本技能及其 references。

## 规范入口与边界

- 开始绘图、修改结构或评审流程前，读取 [流程建模与评审规范](references/modeling-standard.md)。以 BPMN 2.0.2 的执行语义为依据，借鉴 bpmn-io/bpmnlint 的可检查规则；本工作台使用简化表达，不宣称是完整 BPMN 模型。
- 先读项目规则与 [平台存储说明](../../../README.md)，确认当前实例支持的编辑方式。实际改图时读取 [CLI 操作](references/cli.md)，默认用 CLI 拉取、按稳定 ID 批量修改、检查差异并保存；数据字段和原生显示规则见 [工作台维护](references/workbench.md)。MySQL 模式优先使用批量 CLI，文件模式可使用浏览器编辑已有流程。用最新保存版本作为修改基线。
- 规则分为标准语义、可读性约定与项目业务事实。不能把布局偏好说成标准硬约束，不能把某次故障或当前实现推广成所有业务的必经步骤。
- 本 skill 授权范围是资料和流程评审。业务代码改造、对外发布及运行外部业务操作按用户授权处理。

## 全链路映射先确定全局，再改局部

首次映射、按代码版本维护、由图反推实现，或局部变化涉及其他调用方时，先按 [全链路代码映射与版本维护](references/versioned-mapping.md) 建立业务阶段、源码基线、状态读写和跨图承接索引，再动第一个节点。绘制中每个改变结果的分支同步核对来源、所有受影响的接收方和业务后果；交付前的走图用于复核。规则由制图者执行，源码可判断的遗漏、术语和矛盾先自行解决。

## 按读者问题分层

- 业务总览优先沿同一业务对象的生命周期组织，例如“提交草稿 → 编辑审核 → 发布文章”，表达阶段进入条件、结果、等待及异常承接；阶段名称按实际业务确定，不把代码调用树或类目录直接作为总览。
- 重整阶段图时先保留本层业务动作骨架和分支前提，再收敛技术细节；业务读者不应穿过多层通知/重试治理才能找到本阶段核心动作。具体迁移与双向追踪见 [阶段图重整](references/readability-examples.md#阶段图重整保留业务动作骨架)。用户从父图进入后看见互不相连的发起区和结果区时，按 [从父图入口连续读完阶段](references/readability-examples.md#从父图入口连续读完阶段) 修正本层业务因果链；仅有来源/目标关联不等于读图连贯。
- 区分阶段展开、公共模块复用和独立后台：阶段展开回答“这一阶段怎样推进”；调用关系回答“此处复用什么处理、结果返回哪里”；后台流程回答“由谁独立触发、结果交给谁”。导航分组不等于调用链，生命周期阶段也不因能展开就成为同步 `call`。具体判断见 [业务总览与阶段展开](references/modeling-standard.md#业务总览与阶段展开)。

## 问题在相应层级可追踪

- 总览保留会改变阶段推进的风险边界、等待或失败结果，以及下一责任方和详细图入口；不复制模块内每个查询、锁、重试和保存分支。关键风险是否保留，应看读者能否识别“哪个阶段可能停住或产生错误结果、由谁承接”。
- 用于定位问题的详细图必须显式保留具体检查、分支条件、实际或拟议后果及恢复缺口。例如“关联订单未查到 → 仍返回通知成功”不能删除、仅写进说明，或用拟议重试掩盖现状；目标处理标明未实现状态。
- 允许把完整诊断路径收进对应阶段或模块的展开图。总览的业务风险和承接、详细图的触发条件和问题路径应相互对应；不得因分层让风险从总览消失，也不得因强调风险而把全部诊断明细搬回总览。
- 分层核验时分别回答：只看总览能否理解阶段及受阻后的去向；进入相关详细图后能否沿具体检查找到问题原因与未处理结果。方法级证据可在说明中，但不能用聊天或说明补出图上缺失的业务路径。

跨图出入口采用[固定对应标签与逐级反查](references/evidence-to-change.md#固定对应标签与逐级反查)。绘制时就把确定结果接到上层相应分支，保留还缺事实的判断；成对维护出口输出字段与承接节点输入字段。某层接收后还需转交时，先落到该层入口，再沿图内连线到该层出口。批量核验时用随附脚本从主图反查到实际出口。按出口逐个走查或核对输入来路时加 `--explicit-inputs`，再按具体场景复核分支语义。

## 绘图与评审共用的节点语义

绘制初稿、修改现有图和评审都必须使用 [入口、事件与结束范围](references/node-semantics.md)。先判定业务起点、跨图承接、事件触发/继续和结束范围，再选择图形及结构化属性；评审复用同一规则，不另建与绘图脱节的检查口径。已有节点迁移保留 ID、用户说明、位置和有效连线；无法确认的来源/范围保留待核实，不凭标签猜成完整链路。

## 工作顺序

1. **定层级与边界。** 先明确读者要看业务生命周期、阶段推进还是具体问题诊断，再确定对象、触发源、责任范围、起点和结果。总览按业务阶段组织，阶段内部再对照真实调用；区分一个业务实例、一次任务执行及独立调度。
2. **列关系并核两端逻辑。** 对本次涉及的入口、出口、调用与返回逐对核对“来源 → 输出对象/状态/保存结果 → 入口前提和筛选 → 接收后的实际分支 → 最终结果”。按 [出口与入口成对验收](references/evidence-to-change.md#出口与入口成对验收) 核实逻辑兼容；关联可跳转不代表结果被接住。简单路径直接走图，复杂关系在主题文档保留精简映射表，不另造重复规格。
3. **画主干再展开。** 先画本层级的业务阶段或动作及其结果承接，再展开需要解释的阶段；阶段内的代码调用、查询和重试不原样铺到总览。落节点前先区分业务输入、派生接收与独立恢复；遇到发送/接收或跨图调用/返回，先成对画出来源与承接，再补内部步骤。父子图展开同一次分流，不另起一次业务。按 [绘图示例：从一个业务输入展开异步支路](references/readability-examples.md#绘图示例从一个业务输入展开异步支路) 完成初稿。本层级保留正常路径、影响后续的判断和异常；所表达的分叉类型、同步点、异步触发及输出承接必须明确。具体诊断检查放可进入的详细图，方法证据留说明，不能用“后续处理”等模糊方块掩盖缺口。
4. **走图。** 按规范检查结构，并选择与改动相称的正常、失败、未知、并行先后或恢复场景逐步推演。每一步回答当前对象和执行路径在哪里、谁接手、是否重复或永久等待。再从本次争议的等待/异常结果反向追到前置动作与分支条件，按 [原因追踪验收](references/readability-examples.md#从结果反向定位原因) 检查读者能否仅凭图解释为什么走到这里；路径可达不等于原因可定位，也不等于业务验收通过。
5. **提交与分项核验。** 使用 CLI 的 `check`、`diff`、`apply --dry-run` 核对本批内容，再 `apply` 原子保存流程与说明并自动回读。授权改图即可执行本次提交，不额外增加确认环节；版本冲突重新拉取合并，不换版本号强推。涉及结构、布局、文字或跳转变化时，通常在实际画布以可阅读缩放检查主线、分支和调用跳转；用户明确本轮只核逻辑、不看布局时，使用 CLI 和源码完成结构、引用及结果承接核验，不启动浏览器、不追加布局工作，交付注明视觉未核验。需要读图且涉及局部结束、回查或跨图承接时，参照 [可读性正反例与读图验收](references/readability-examples.md)。仅沿画布辨认下一步、等待关系、结束范围及恢复来源；修正误导性的形状、重叠、穿节点连线及截断。结构走查与读图检查分别记录结论，画面问题仍用 CLI 修正并核对保存结果。仅说明文字等不影响画布的修改可复用原视觉证据，交付明确资料更新与实现状态。

## 源码建模与争议先收敛证据

- 依据源码绘制/核验业务流程，或用户追问节点含义、检查对象及必要性时，先读 [从源码到最小改图](references/evidence-to-change.md)，查清当前入口、前置条件、真实检查及父图承接，再修改。不要等用户指出悬空结果才检查业务责任，也不要用更多抽象节点或聊天解释延续原歧义。

## 证据与方案

- 区分原有源码、评审分支、现场已观察事实、推测和待评审建议。记录版本与核验时间；没有部署证据时不能把分支能力画成生产现状。
- 源码一致性与业务闭环分别给结论：准确复刻代码不代表符合产品要求。源码存在无人承接的分支时，图应显式揭示缺陷；既有评审未识别时，同时承认评审漏项，不能以“代码就是这样”免责。现状缺陷、图上缺失和证据不足的判定见 [双重评审](references/evidence-to-change.md#源码一致性与业务闭环分开评审)。
- 问题使用稳定 P 编号，写明触发条件、受影响对象和方法级依据；不因新讨论随意重编号。
- 用户要求在原图评估优化时，在原阶段接入拟优化判断和出口，不另造与原图脱节的一组方案图。重复子图仅在授权或明确无用时收敛，保留历史恢复能力。
- 历史对象处理或人工介入只在适用时进入，画出条件与跳过后的去向；“无记录”“无需处理”“已接管”均不自动等于整条业务完成。

## 分叉、后续与结束

绘制或评审分叉、多入线时，共用 [并行分流与汇合](references/parallel-merge.md)。仅修改存在歧义的节点；没有等待依赖不添加汇合，普通业务动作不能因多入线被替换成纯汇合。

- 普通方块多条出线不能作为本工作台“已经清楚表达并行”的证据；多条入线也不代表等待全部完成。显式区分条件择一、全部启动、按条件多选、先到事件、等待全部及直接汇入，详见规范。
- 不等待后台的主线需有独立可追踪的后续。不得为了视觉连通，改成“后台无结果后才启动”，也不得跳过校验、下发与确认直接到成功状态。
- 使用结束样式前确认结束范围与后续责任。普通支路结束、子流程结束、全业务完成、取消其他执行是不同语义；合法的局部结束可以保留，但图上必须看得见其他仍在继续的路线。
- 子流程结束后父流程可以继续；跨图输出也可以是继续出口。依据实际语义选择表达，不要求所有输出一律是结束节点，也不禁止所有子流程使用结束节点。输出与父图承接必须成对核对。
- **跨图继续使用跨图出口。** 当前支路把控制权交给父图/其他图继续时，使用 `output` 专用出口形状，并关联明确的目标流程和节点；不能只把普通步骤改名为“→ 主图”，也不能用全局结束样式暗示全部工作结束。绘制时先配对出口与承接，评审时再验证跳转、返回和结束范围。具体规则见 [跨图出口](references/modeling-standard.md#跨图出口)。
- 用户指出“看起来停了”“不知道走哪条”时，先修正结构、连线或局部布局；不能反复用聊天解释为画布歧义辩护。
- 用户问“可追踪是什么意思”“状态变了指什么”时，按 [具体条件表达](references/readability-examples.md#分支条件写成可核实的事实) 核对检查对象、事实条件与结果去向；不要用另一组抽象术语替换，也不因优化措辞推定现有保障已经实现。

## 复杂判断与场景演练

涉及多条件组合、共享业务判断、结果覆盖争议或逐步演练时，读取 [规则表、覆盖检查与场景演练](references/decision-rules-and-rehearsal.md)。按“输入条件 → 业务结果 → 本调用点后续”组织规则，复用已有枚举和测试来源；分别记录模型检查、原型演练与真实业务测试结论。简单判断仍直接用清楚的分支表达，不要求每个节点建立规则表。

## 公共模块与调用

- 先区分归属、调用和独立异步：归属组织定义；同步调用执行该定义并返回当前调用点；独立后台由真实事件触发。方法封装不证明已异步解耦。涉及复用时读取 [模块定义与调用](references/modeling-standard.md#模块定义与调用)。
- 同一公共定义维护一份，调用节点引用该定义；每处调用分别保存输入对象、模块入口、结果及本图返回点。公共模块不因被某个子流程调用就归属于它，也不把返回写死到某个父图。输入、返回数据与接收分支写入 [右侧参数与承接说明](references/workbench.md#右侧参数与承接说明)，画布保留业务动作和去向。
- 来源不同但连续处理相同时，从最早相同动作或调用处收敛，不只合并末尾判断；保留每次执行的对象、次数及调用上下文，共用图定义不等于合并运行实例或等待两路。合并条件与反例见 [连续处理段去重](references/modeling-standard.md#连续处理段去重)。
- 公共调用放在实际使用该能力的业务阶段中，总览仍按生命周期推进。详细图保留本轮问题的检查与异常后果，总览保留业务影响与承接。工具未支持的关系明确列为缺口，不能只写“复用”便报告已建立调用。

## 父子与异步关系

- 跨图承接与事件样式按语义统一：阶段展开中的结果观察/接收使用 `input`；真实消息、定时、人工或响应发生才使用 `event`。不能因标签含“返回”就设双圈，也不能因存在 `source` 就把真实事件全部改成入口。核查方法见 [入口语义](references/node-semantics.md#跨图承接与事件样式的判别)。

- 复核子图入口时区分父图业务输入、同次分流派生的异步接收、独立恢复入口。派生接收必须在画布上追到发送动作并标明对象关联与异步边界；父子图是同一次分流的概览与展开，不重复触发。不要机械要求所有子图只有一个开始节点，详见建模规范的“派生接收与父子入口一致性”。

- 子流程明确输入的来源、对象及条件；定时、消息、回调和人工操作各自标明真实触发，不能伪装成上一节点直接调用。
- 从每个子图输出核对实际调用点或异步接收方、对应出边、接收节点与后续处理；公共定义有多个调用点时逐处核对，不能默认全部返回归属父图。对象、状态和条件一致。已有承接能准确表达时复用。返回导航、单独一段说明或只有输出标签不足以证明父图接住结果。
- 同步子流程中的完成可返回父调用节点；父图线不能直接穿进子图内部。若工作台子图只是展开说明，应明确对应同一动作/分流，不能暗示再次执行或等所有后台完成才继续。
- 异步投递、可靠接管、业务执行完成分别建模；标明原任务关联和结果到达的接收位置。真正独立的后续使用独立入口和触发条件，不能画成同步返回。
- “依赖恢复后/条件满足后/稍后重试”只是条件，不是触发来源。必须能在图上找到谁检查、由定时/回调/人工哪个入口触发、恢复依据是什么、同一对象接到哪里，以及仍未恢复时的出口；具体检查见建模规范。
- “本次退出、等待回扫”必须同时核对结果承接与原任务再进入路径，不能只写等待文案就判定闭环；父子图需能对应同一原任务、外部接收位置和真实恢复入口。参照 [等待出口的双向追踪](references/retry-lifecycle.md#等待出口的双向追踪)；多个等待出口共用真实调度时，用统一跨图出口关联 [公共定时入口](references/retry-lifecycle.md#公共定时入口的统一表达)；等待与定时规则在公共流程内部体现，不另造恢复样式或等待模式。读者混淆返回与下一轮执行时，按 [本次返回与下次触发的可见区分](references/retry-lifecycle.md#本次返回与下次触发的可见区分) 调整画布。
- 同一调度或任务在父子图出现时说明概览与展开关系；不同职责不能只因名称相近合并。迁移节点或连接时保留稳定 ID、说明、引用和历史。

## 异常、循环与资金副作用

- 故障名称依据真实失败阶段、对象和结果，不以服务/模块归属充当业务异常类型；命名、判别能力与承接的核验规则统一见 [故障原因与模块归属](references/evidence-to-change.md#故障原因与模块归属)。

- 存在扫描、轮询、重试、等待或补证恢复时，读取 [循环与接管闭环](references/retry-lifecycle.md)。区分任务接管、本次退出与业务完成；未决状态明确恢复入口和触发条件，不用无条件循环隐藏未完成。
- 一笔异常可能影响其他订单、消息或心跳时，读取 [异常传播与退出复核](references/exception-containment.md)。追到调用者、事务及消费者外层的确认、锁释放和下一笔处理；前置检查及异常保存自身也要有失败出口。
- 每个退出口都要核对业务结果：正常推进/完成，或异常已可靠登记且可见并有后续责任。技术通知成功、任务提交、日志成功和局部结束不能替代业务结果；有界等待须能追到原对象、处理者、期限、恢复入口及超期去向。异常登记失败本身必须显式失败并保留恢复依据，不能假报已进异常单。
- 按实际风险覆盖成功、明确失败、未知、读取失败和超期。“离线/无记录”不能自动推断“未发生”；通知成功不等于业务完成，转人工不等于完成。
- 涉及资金或设备副作用时，检查原请求查询、幂等、迟到事件、跨入口并发和重启恢复；不能以新增补偿绕开原保护或重开重试预算。参数沿用项目确认口径，不捏造统一常量。
- 人工路径明确可见入口、允许动作、结果回填及再核验。人员认领、期限和升级按用户确认的协作方式，不自行新增管理流程。

## 视觉与状态

- 工作台绘图约定：步骤方块使用直角矩形，不使用圆角卡片；判断、开始和结束仍按各自语义区分。这是本地视觉约定，不宣称 BPMN 活动的标准符号是直角矩形。
- 默认白色表示现有逻辑，蓝色表示待实现建议；节点或流程范围明确实现状态。需要同图比较评审分支时可用紫色，但必须有版本且不能冒充已验收或部署。
- 现有工作台默认：灰实线为现有关系，红实线为证据确认的实际路径，蓝虚线为拟优化，紫实线为分支路径。颜色和虚实已用于证据状态，不能再仅靠虚线表示消息、等待或异步；关系类型另以节点和标签明确。
- P 标记表示问题位置，不表示相关代码全部未实现。使用编辑器原生可编辑样式，不把语义只烘焙到截图。
- 节点、出线、参数和说明对同一个对象使用同一个名称。涉及两份投稿时，明确“已提交的版本”和“本次修订的版本”，标明审核或通知结果属于哪一份。核对迟到事件是否应继续作用于原版本。
- 布局按责任与主次分区，主线保持连贯；名称简洁，条件靠近出线，技术证据留说明。必要业务条件不能为缩短文案而删除。规范中的可读性检查不通过时，不能因结构保存成功就宣称图已完善。

## 交付与规范维护

- 更新同一主题的评审说明、规格索引及受影响节点说明；结构修改后核查相关父图与直接子图，避免全工作区无界扩查。
- 交付说明改了什么、哪些关系已核验、仍有哪些待确认或工具限制。区分“资料已保存”“模型走查通过”“业务验收通过”“已部署”。
- 修改本 skill 的建模规则时，用 [规范校准场景](references/review-cases.md) 检查是否引入相反错误；日常小改只复核受影响场景。静态检查、人工推演及真实仿真分别报告，不伪称安装或运行了 bpmnlint/token simulator。

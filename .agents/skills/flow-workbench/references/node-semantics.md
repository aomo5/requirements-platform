# 入口、事件与结束范围

本规则同时用于绘图和评审。形状与标识是本工作台的简化约定；不宣称完整 BPMN 支持。颜色仍表达现有/待实现/分支状态，不兼任触发类型。

## 节点选择

| 语义 | 表达与属性 | 绘制及评审要求 |
| --- | --- | --- |
| 业务起点 | start，开始形 | 谁首次发起哪个业务实例；不得用来表示子图承接或调用返回 |
| 跨图入口 | input；普通入口由 source 指定来源；公共模块入口由调用点指定 | 对应同一次执行，不新增业务实例；公共入口不固定 source 到单个调用者，依据调用上下文追踪 |
| 业务阶段展开 | step 表达阶段，相关图通过归属/展开关联组织 | 阶段按业务进入条件与结果推进；可跨多次事件，不因有展开图就成为同步 call。导航归属不证明执行或等待关系 |
| 公共模块调用 | call，call 指定模块入口和 returns 映射 | 归属与调用分离；同一定义多处引用，输入对象和每个返回结果明确；本次同步返回不等于异步业务完成 |
| 返回调用处 | return，位于公共模块，无固定 target | 按当前调用点的映射回本图后续；独立定时/人工入口不得无调用上下文地返回 |
| 消息事件 | event，message | 发送动作、对象关联、接收边界可追踪；投递成功不等于实际到达/可靠接管/业务完成 |
| 定时事件 | event，timer | 标明调度者、周期/到期条件及原任务；配置未知明确待核实，不补造调度 |
| 人工事件 | event，manual | 哪个角色通过哪个操作入口触发，后续核验与结果回填明确 |
| 响应事件 | event，response | 关联原调用和响应来源；同步返回不是独立业务开始；异步回调按真实协议建模 |
| 跨图继续 | output，target 指向具体节点 | 与承接成对，不能用“→ 主图”普通方块或结束节点替代 |
| 结束 | end，endScope | execution 本次执行；subprocess 当前子流程；business 业务完成；terminate 终止当前流程范围内其他执行。未确定时 unspecified |

事件另有 eventPhase：trigger 为触发一次处理；intermediate 为原处理继续。触发事件单边框，继续事件双边框，附消息/时钟/人员/响应标识和可读类型名称；不能仅靠图标判断。一个业务图可有多个真实事件入口，不机械删成单入口。消息接收和回调事件可用 source 关联图中发送/返回节点；定时、人工无图中来源时说明真实触发者。

## 跨图承接与事件样式的判别

- 先追来源节点及本图后续：若只是把另一图的业务结果接入阶段概览或展开，没有新增消息接收、回调或调度事件，使用 `input`。标签中的“观察”“返回”不能单独证明是响应事件。
- 跨图入口说明“从哪里接到什么状态的对象”，步骤说明“对对象执行什么动作”。同一节点混合入口、检查及循环回跳而引起歧义时，拆为入口→检查动作；本图内部及后续轮次直接进入动作，不绕回入口伪装成重新进入业务。无需为所有步骤机械增加入口节点。
- 真实事件可以有跨图 `source`；例如同一定时触发的概览与展开、异步消息接收及原调用响应。不能按“有来源”批量替换为入口，也不能把概览与展开理解成发生两次事件。
- 双圈来自统一的 `event + eventPhase=intermediate` 渲染，不是跨图入口的另一种皮肤。确定为入口后改节点类型并移除残留事件属性，保留 ID、来源、坐标、说明及有效连线；不要为修单个节点另写 CSS。
- 发现误用后检查同主题的其他事件及带来源节点，按具体语义修正；合法事件保留，证据不足先核实。检查原同步返回是否仍回原调用点，不能为统一样式改写业务返回或重复触发处理。

## 结束范围

- execution：本轮扫描无候选、本条消费退出、本次核验失败等；原任务或业务可能仍未决，必须能追到后续责任和恢复入口。
- subprocess：当前子流程已结束；父流程是否继续按调用语义判断，不能据此宣布全业务完成。
- business：当前业务对象的完成条件已满足；通知成功、退款在途、异常已留存都不是业务完成。
- terminate：只有明确终止当前流程作用域中其他执行的真实语义才能使用，图上明确作用域；普通失败/退出不能套用。
- 未确定范围保留 unspecified 并提示待明确，不自动把旧 end 升为业务完成。真实跨图继续改出口，真实局部结束保留结束形。

## 来源与去向

业务总览的阶段与详细图是概览/展开时，不重复触发或执行分流，也不把长期阶段解释成一次同步调用。入口来源可以关联父图分流节点，不要求把真实分流节点强改为出口；是否需要独立端口按实际层级表达。入口/出口的导航只是定位，业务连线和条件仍须一致。

来源/目标必须指向稳定节点 ID。删除、不可用、未关联要可见提示，不静默退到图首页。允许未完成草稿，但不能通过完整性评审。图形、标题、类型/范围标识和导出应一致，Mermaid 元数据应保留，不只在侧栏解释。

## 绘制与评审顺序

1. 先确定本图的业务层级，再区分一个业务实例、一次调用/任务执行、阶段展开和独立触发。
2. 为跨图入口/出口配对来源与承接，事件明确类型、阶段和对象关联。
3. 对每个结束追问结束谁、谁仍运行、未决由谁恢复；再填写范围。
4. 从每个入口正向、从每个接收逆向走图；交换并行完成顺序，验证不会重复触发或误判全局结束。
5. 保存后重读，检查类型、关联、调用映射、阶段和范围保留；按本轮授权核验跳转及导出。用户明确不看布局时用 CLI 核对，不启动浏览器，记录视觉未核验。

## 知识库投稿示例

- `review/entry` 关联 `submission/queued`，表示从提交进入审核阶段。
- `review/approved` 使用跨图出口，指向 `publish/entry`。目标确认同一篇文章已通过审核，再进入发布。
- 审核超时扫描由定时事件触发，按原稿件 ID 查询待审核记录。人工恢复通过编辑的操作入口触发。
- 发布任务受理后，本次调用可以结束，文章是否已发布由原任务的结果继续核对。

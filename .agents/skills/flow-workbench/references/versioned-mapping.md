# 全链路代码映射与版本维护

用于首次把一条业务链映射为原生流程、按新代码版本更新、从图反向形成研发改动，或处理“改这里是否影响其他地方”。以下动作由制图者在开画前和绘制中完成。用户只处理证据无法决定的业务取舍。

## 动笔前先建立整条业务链的边界

1. 固定源码仓与完整 commit（多仓分别记录）、相关配置/环境、需求范围、已确认决策及工作台图和说明版本。明确依据是发布版本、评审分支还是工作副本。有未提交的相关代码时单记差异。以项目部署记录认定发布版本。
2. 从用户实际进入的主流程开始，顺着同一个业务对象列出所有阶段、进入条件和结果。查清谁创建对象、谁写状态、谁读取它决定下一步；列出可能停住、结束、退款、转人工或重新进入的位置，按真实业务取舍。同步方法、接口、事务提交后派发、独立消费/轮询和人工操作分别记清。每个跨界点记对象关联键、发起方、接收方/选择规则和接收数量、输出及后续承担者。未知处留具体断点。
3. 从源码查入口、调用方和所有实现，补查没有直接方法调用的路由配置、共享表/状态的读写、定时任务、消息、设备回报及相关枚举/Mapper。对照全主题图找遗漏。已有图先用 CLI 拉到新临时文件，运行：
   ```sh
   python3 <本技能目录>/scripts/flow_context.py <CLI草稿> [--flow 流程ID]
   ```
   命令列全主题目录，区分归属、调用、各调用点返回、输入来源、输出承接和恢复。聚焦某图时仍从全主题查直接关系。按发生变化的结果继续向外展开，并查跨需求消费者；归属关系只说明到哪里展开。旧图未画的源码分支须另补。
4. 用以上信息形成一份可复用的全链路索引。每个阶段记录“从哪里来｜输入/状态｜本阶段做什么｜谁接结果｜源码位置｜图/节点 ID｜已核/待核”。已有版本化规格或映射记录就地维护，避免重复抄图。全链路索引先覆盖业务起点到最终结果，再选择本轮要展开的高风险切片。局部改动先注明它在整条链的哪个位置、会影响谁、哪些边界可复用已有证据。尚不清楚由谁接手时可画已核部分，给边界留待核标记，禁止接到臆测的成功终点。

## 绘制中按同一笔业务把上下游一起画

- 每画一个会改变执行结果的判断，在同一批补对触发条件、真实分支/遗漏的分支、读写对象、副作用及直接接收方。关键接口/枚举在节点参数中写清业务含义、来源、允许值和空值/未知值的代码行为。多个入口使用同一处理时，分别核调用上下文、入参、返回值和各自下一步。
- 同步调用在每层调用点接住本次返回。异步按实际触发分别画发送、接收及状态写入；父流程凭后续事件或读到的业务状态推进。重试沿持久化对象追到再次进入的触发，还要覆盖耗尽的去向。分别记录请求已收到、任务已完成、订单状态已改变、资金已核清的可观察依据。
- 按源码列出所有会改变行为的条件、早退、空结果、异常、边界值、重试及副作用，再逐项找到节点或出边；反向从图中每条现状业务分支找回源码依据。按范围登记已映射、经核实在范围外、未映射和证据不足的分支。覆盖数字基于该版本源码中的行为分支，流程/节点数量只描述图的规模。细节放入可展开模块。发现未实现的理想处理，保留现状后果并标目标版本。事实、目标和测试记录分别维护。
- 一项输出或契约变化时，覆盖全部调用方、读写同一状态的其他入口与相关测试，沿受影响结果递归追到业务终态、明确接管者或已登记的缺口。设计目标改动时，把它代入同一业务链，在落节点时先推演成功、失败和迟到/重复执行对后续订单、资金及设备的影响。遇循环按“调用点、对象、状态”去重。若边界输入、输出、时序与副作用均有证据等价，记录理由即可复用下游；不因图上相邻而重画无关模块。
- 一个事实有多种展示时，同批核节点、连线、节点参数、说明及父图摘要。业务决策用稳定 ID 保留依据和确认版本。用户已经决定的事项只有新证据或主动变更才重开；发现同类返工，加入能重现误读或失败的反例，再查同主题里它的其他调用处。

## 绘制当前版本时，按一次真实执行走通

- 同图比较现状和目标时，从用户进入的主图选一条具体路径，暂时跳过待实现节点和出边。沿同一对象、同一次触发走到实际返回方、业务结果或已证实的断点。逐层保留请求来源，例如渠道推送需要回复发起方，主动查询则返回查询方；两者复用一次处理后仍各走自己的出口。首次绘制和保存回读都这样走一次。
- 同一状态值可能来自“本来就是这个状态”或“这次写成这个状态”。把读前状态、写入条件、是否实际写入及副作用分开。两路可以共用后续动作，入线须保留各自已经做过的事。涉及并发时核对首次读取、加锁后复读、条件更新失败及调用方解释；按代码可推得的交错标“静态可达”，取得运行证据后再标“已复现”。
- 遇到重复投递，分别查事件来源、持久任务、接收接口和业务动作各自用什么标识去重、有效期多久、超出哪一层保护后会继续做什么。断言某一层只执行一次时，把测试标在该层；对其余可能产生设备或资金动作的路径留下具体待验项。

## 按版本交付和增量维护

- 从主入口正向推演正常及高风险路径，再从异常结果反查原始订单、触发和条件。必要时让未参与绘制者只按图推演。与绘制责任分开记录：源码分支已对照、图结构可走通、实际业务测试通过、生产已部署。发现线上无恢复路径也可以是忠实映射，记录影响与责任，不虚补成功或恢复。
- 每个已覆盖范围至少能查到版本组合（源码 commit、图/说明版本、环境/生效配置），稳定规则/节点/边 ID，及真实测试的用例、断言、运行记录。真实测试显示通过必须有该版本/环境对应的断言证据。仅经过、未测、失败、旧结果待复核分别显示；保留图上现状/目标的颜色含义。工作台尚不能展示的维度用已有关联记录明示。
- 后续版本从上次基线比较代码、配置、接口、枚举及数据库变更；映射新增、删除和改变的行为。图先改时记录目标行为差异与验收断言，再交研发按授权改代码。发布前用实际实现反查图，发布后按部署证据登记新版本。旧基线、旧测试与已确认决策保留可回查。
- 首个可读版本按一段端到端业务交付。随批交付覆盖范围、可复用证据、未覆盖路径及真正待定的业务问题，避免逐节点找用户纠错。对证据可判的事实与可读性问题由制图者先查清并修正。发现数据缺失时明确缺哪类证据；只有业务上存在多个合理结果时，把选项、影响及建议汇总给用户一次决定。

## 把断言写到它验证的那条路径

在用户关心的分支或结果旁，用短标签写出“测到哪里／还要验什么”。详情里关联源码版本、环境、运行记录和实际断言。校准可用两个例子：

| 手中证据 | 对应的图上标记 |
|---|---|
| 测试断言接收端缺单仍回成功、设备启动调用 0 次，断言通过 | 现状边标“缺陷已复现”；目标失败响应、重试与耗尽接手分别保留待验范围。 |
| 用例断言投稿接口返回和稿件 ID，发布结果只写进日志 | 标“投稿接口已测，发布结果待验”。把其他稿件类型和权限分支的证据归到各自路径。 |

若多轮复跑或多个执行者补证，用最终逐项报告按用例身份去重，保留不同版本、环境与参数场景的区别。由图的保存者在提交前核一次最终证据清单，并在服务端回读版本上复核节点、连线、说明及关联资料。测试数量在一处维护；需要在图上展示时优先写具体验证结果，减少多处转抄中间数字。

# 循环与接管闭环

用于周期扫描、异步确认、补偿、轮询及人工补证后的恢复。先核对当前流程与已有实现：缺在图上、说明里还是业务实现里，分别记录；解释“应该如何处理”不能作为“原图已经处理”的证据。

## 检查同一对象下一次进入时会发生什么

- 区分全局调度持续运行与单对象反复执行。按业务身份去重，分清未接管、有效执行中、等待下次执行、待补证、已完成；不要把“已完成”和“处理中”合成同一业务结果。
- 可靠保存后才确认接管；写入失败或结果未知保留原触发源及可重新发现的依据。检查调度写回、游标推进与重启恢复会不会漏掉失败对象，当前对象退出后其他候选如何继续。
- 符合扫描条件只表示发现候选，不等于可靠接管或业务完成。核对原对象与原任务并可靠保存处理责任；需要执行权时取得执行权后才确认接管。
- 回调、扫描、重启与手动恢复共用原任务身份及幂等入口。重复进入不能重置首次时间、次数或预算；租约过期不代表原执行停止，旧执行或外部结果未明时不重叠执行副作用。
- 每次再次进入都同时核对触发源与允许条件：谁由定时、回调或明确操作发起，检查哪个依赖/原任务，结果满足什么条件才继续。仅写“依赖恢复后”“有新证据后”不算触发机制；按 [建模规范的恢复来源检查](modeling-standard.md#恢复条件必须有真实触发来源) 补齐检查动作、接收节点和仍未恢复的出口。不能把结束点到独立调度画成顺序回跳，也不能无条件重进副作用入口。
- 等待或异常本身不触发独立扫描时，不画从该出口直接触发扫描的箭头；用本次退出、可重新发现依据和独立入口的触发条件表达衔接。
- 自动执行明确采用什么次数或期限边界，沿用已确认策略；缺参数时列待确认，不捏造统一常量。耗尽或超期退出本次执行并保留可见异常；列表持续展示不应触发自动重试，超时不能推断资金或设备业务失败。
- 自动预算耗尽后的补证与明确安全重试要有真实恢复路径：先核原执行、原请求和新证据，按原任务单次核验或已确认的恢复策略执行。既不能偷偷重开自动预算，也不能因旧期限已过而立即退回待补证、导致补证后仍无法推进。
- “扫描结束”“通知完成”“可靠接管”与“业务完成”分开。资金处理中应有独立原请求查询、到期调度及超期可见出口；消费者退出不等于资金查询责任结束。
- 通知成功仅表示收到约定的成功响应；是否已进入业务或可靠接管要核对实际契约和实现。若回调已触发处理，返回后的父流程应跟踪原任务和结果，不能无条件重复发起同一业务副作用。

## 从产品结果审查退出口

- 对结束、跨图输出及模块返回，沿同一业务对象追到正常推进/真实完成，或异常记录可查询且有后续处理。临时等待只在原对象、实际处理者、期限、再次触发和超期出口都明确时成立；“仅本次结束”不是免责说明。
- 通知成功或任务受理后仍需跟踪实际业务结果。若成功记录退出通知回扫，独立发现必须覆盖这些记录，不能只补失败/耗尽通知。内存任务与执行日志不证明重启后有人接手；没有实现/启用证据，标未闭环而非推断自然恢复。
- 核查异常单真实查询条件，尤其创建中、缺少业务订单、部分退款未决等对象是否可见。登记动作、保存成功、列表可查分别验证；不能为凑列表条件伪改订单状态。登记失败需明确报错、可达的故障报告和原持久化来源恢复，不能只写“保留日志”或假报已登记。
- 现状诊断图可保留暴露缺口的端点，但标明不符合目标验收；目标去向单独标待实现。不要机械删除所有局部结束、把通知成功改成再启动，或把超期当成可以直接退款的证据。按本次涉及对象审查相似出口，不扩建无关治理平台。

## 检查回路的可读性

- 看到检查与判断之间的“双箭头”，先核实是否为两条相反的顺序边重合，不能据外观解释成并行或双向调用。正向检查与有条件回查应分别可追踪，不以聊天说明替代路径修正。
- 确有等待间隔时，表达为“检查→结果判断→未确认且仍允许继续→等待原下一检查时间→再检查”。从侧边回到实际检查动作，不回跨图入口或再次下发业务指令；沿用同一对象、原次数和截止时间，耗尽/超期及执行异常各有出口。内部等待不自动变成独立定时任务。
- 没有真实等待动作的即时循环，只分开线路并标条件，不为避开重合而编造暂停或调度。修正前后核对执行次数、触发源和副作用不变；仅移动两节点不一定能分开重合的对向曲线。

## 等待出口的双向追踪

遇到“本次退出／等待回扫／稍后重试”，分别沿图检查两条关系：

- **结果往哪里交。** 若结果需要交给父图或外部流程，子图明确输出，接收图有对应出边、接收节点和结果含义；仅写“输出”或提供返回导航不能代替实际承接。纯内部等待无需凭空增加外部输出。
- **原任务怎么再进来。** 从真实定时、回调或人工入口追到重新发现／读取原任务、允许继续的条件及执行入口；能对应等待出口留下的同一任务及持久化依据，不重开预算。结果已交给父图并不等于恢复责任已经落实。
- **跨图如何对上。** 恢复机制在子图展开、父图只有等待结果时，应在所需评审层级显式给出恢复入口或清晰的跨图承接，使读者能沿图追到下一次处理；已有等价入口直接复用。同一调度的概览与展开应明确对应，不能新增第二套调度，也不能画成等待出口启动定时器。
- **恢复失效会怎样。** 调度启用、周期、停机恢复或保存失败后的可重新发现性没有证据时，按影响在图上保留待核实及持续等待风险，说明中记录证据缺口；不臆造健康探测、告警或自动恢复。只改结束形状、换文案、添一个没有接入路径的定时节点，都不足以证明闭环。

读图验收：从等待出口能指出结果接收位置，从真实恢复入口能追到同一原任务的下一次处理；两者不得被一条无依据的立即回跳替代。局部执行确已结束时仍可使用结束节点，不强制所有等待输出改成步骤方块。

## 公共定时入口的统一表达

- 用户已确认：等待由公共定时流程承接时，调用处统一使用现有跨图出口形状和 `output.target` 关联操作。定时入口本身按周期触发，等待、到期筛选与执行规则在公共流程内部体现；不因异步语义另造恢复节点、恢复标记或调用处等待模式。
- 同一真实作业只维护一份独立后台流程；关联不改变作业归属，也不表示当前节点立即启动调度。不同扫描对象、筛选条件或执行者不能只因都“定时”就合为万能作业；公共定时流程也不等于同步公共模块 call/return。
- 公共流程内能追到“真实触发 → 查询原任务 → 状态与到期条件 → 防重检查 → 执行入口”，无候选、查询失败及不再允许重试分别有去向；沿用原任务、次数与期限。调用处不重复展开内部等待规则。
- 双向核对出口目标和来源，保持当前对象及持久化依据一致。调度启用、周期、未保存任务的重新发现或停机恢复未核实时明确待核；统一形状与关联不等于运行保障已落实。内部 sleep/循环仍按原执行表达，不强行新增定时任务。
- 迁移原等待结束点保留ID、位置与说明，设置output/target后移除不适用的endScope/recovery。带真实业务动作或其他出线的节点按实际职责保留，不为追求外形一致丢掉异常承接。
- 全主题复核要同时检查等待出口、父图接收、公共入口及本轮结束四层。公共流程内部已写明下次触发、筛选及失败规则的本轮结束可保留；调用处不能只写“原任务继续”而无公共入口关联。重复的定时概览应关联同一维护源，不各自保留一套触发规则。
- 未知恢复来源先辨明原消息、通知记录、扫描候选或人工异常；未保存、已耗尽、超筛选范围和启用未核实不得虚构自动重试。异常保存失败须报错，不能回跳到同一保存入口形成无限循环，也不能跳到人工列表假装记录已可见。

数据与 UI 操作见 [跨图出口数据与编辑](workbench.md#跨图出口数据与编辑)。

## 本次返回与下次触发的可见区分

适用于读者沿“定时回扫 → 派发 → 公共调用 → 跳过”阅读，误以为模块返回会立即回到扫描判断的情形。

- **本次返回指出接收位置。** 保留原生 `return` 和调用处 `call.returns`，在画布可见位置显示本次结果及返回的调用方／接收节点。不要只在说明中写“返回调用方”。优先使用现有返回导航；当前只有一个已核实调用点时可用简短名称辅助阅读，多调用点仍按实际调用上下文返回，不能把公共返回改成固定 `output.target`。
- **等待出口明确本轮结束。** 沿用现有 `output.target` 关联，名称可写“本轮结束，原通知等待下次回扫”，将可点击入口表达为“后续入口：支付通知定时回扫”。这是导航到后续责任所在流程，不是立即执行边；不从出口拉顺序线回查询判断，也不另造恢复模式。工具只有普通目标导航时，利用现有文案与布局表达区别并如实说明限制，不擅自改编辑器。
- **下一轮保留独立定时事件。** 入口如“下一轮定时触发”，再接查询、状态与到期筛选、派发。与本轮结束在空间和名称上分开；启用、周期等配置事实或待核项保留在对应说明中。不得为追求直观编造周期、删除必要筛选，或把所有出口都接回定时任务。
- **跳过之后按原任务状态承接。** 次数失配只表示当前执行依据已过时。图中已有当前状态核验时直接复用：仍可重试等待下次到期，成功核对原业务结果，耗尽交既定异常处理，缺失／读取失败进入故障路径；不要因为本次跳过就重发、增加次数或宣称成功。已有其他可靠承接时不强制增加重复查询。

读图复核只需沿受影响路径回答：跳过返回哪个节点；本轮在哪里结束；谁触发下一轮；原任务凭什么再次被选中；成功与耗尽为什么不再普通重试。至少走“等待下一轮”和“成功或耗尽转其他处理”两类，避免只验证导航链接可点。周期性扫描与同一任务的无界重试分别判断；接口错误持续发生时仍需沿既定异常路径核验，不能因存在次数上限就笼统声称所有路径都会终止。

## 画到原图并检查相似节点

主图保留关键分支；详细状态与恢复条件接到原子流程。至少在图上能追到本次退出、等待的恢复入口、业务完成或持续未决。说明保存字段、预算来源和证据，不用长节点替代判断与连线。

发现一处漏项后，检查同主题其他扫描、确认、通知、资金查询及人工恢复节点是否有同类无条件循环或责任断点。仅补有依据且属于授权范围的缺口；不把检查扩展成全系统重建，也不把方案标成已实现。保留原稳定 ID、说明、已有保护和历史。

选择与修改相称的场景复核：重复扫描与回调并发、任务已执行但写回失败、重启或租约过期、预算耗尽、补证后恢复、已完成再次到达。方案阶段核查流程与真实渲染；业务验收另按环境与权限执行。

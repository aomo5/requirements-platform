# 流程评审示例

以下场景以虚构的知识库投稿说明如何核对模型。按本次改动选择相关行，再从入口走到业务结果。

| 情况 | 核对什么 |
| --- | --- |
| 提交后同时建立审核待办和发送提示 | 标明两路都执行。审核主线由已登记的待办承接，提示失败走自己的处理分支 |
| 两条路汇到发布 | 核对是互斥结果到达即可，还是内容与权限两个检查都成功才继续 |
| 子图同时有消息、定时和人工入口 | 每个入口标明触发者、稿件版本和真实条件，分别追踪至对应后续 |
| 公共校验被草稿提交和退回重提调用 | 共享一份定义。逐调用点核对输入、返回类型和结果接收位置 |
| 发布任务已受理，结果尚未返回 | 区分本次调用结束和发布完成。沿原任务找到再次检查的触发源 |
| 等待出口链接到公共定时流程 | 将待查状态、到期条件和对象 ID 代入目标筛选，确认原记录确实会被选中 |
| 查询失败与没有记录画成一条路 | 核对两种事实的后果。为依赖异常和数据缺失画出各自的去向 |
| 返回合写成“稿件已处理” | 保留已发布、审核退回、发布未决等会改变后续处理的结果 |
| 保存待办失败，图上却显示“交人工处理” | 核对待办写入结果以及人工列表是否可读。将登记失败接到实际异常入口 |
| 重试发现稿件已更新或原任务超期 | 从原稿件版本、首次提交时间和当前执行状态判断后续，沿用本轮的重试范围 |
| 审核与发布放在不同子图，入口跳得通 | 逐条核对出口事实、输入对象、接收节点和接收后的分支。路径应说明为何到这里 |
| 两个入口都调用相同检查，再进入同一批结果处理 | 比较输入、返回、副作用和责任，符合共用条件后收敛重复段，保留每次调用上下文 |
| 图中展示新增的超期扫描 | 将计划的作业职责、触发和筛选写清。把对应实现和验收证据标为待补 |
| 预演覆盖通过、退回和未知 | 分别记录静态结构、读图推演和真实测试证据，以及各自覆盖的版本与场景 |

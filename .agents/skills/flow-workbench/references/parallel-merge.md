# 并行分流与汇合

绘图和评审共用；本工作台的结构化类型是表达工具，不会让业务自动获得并发、同步或幂等能力。

| 模式 | 每次到达后的语义 | 图上要求 |
| --- | --- | --- |
| split：全部执行 | 所有出路都启动，各自推进 | 明确各路执行范围；不暗示必须同时开始或相同线程；异步投递仍需真实来源与接收 |
| join：等待全部 | 同一实例/同一轮次的每条必需入路到齐后，才继续 | 列清要等哪些路、关联哪个对象和轮次；检查异常、跳过、取消时是否仍能到齐 |
| merge：每次到达即继续 | 每次入路到达都继续，不等待其他路 | 不表示首个胜出、不取消其他路、不去重；两路都到可能下游执行两次 |

## 绘制原则

- 只有需要等待多路共同结果时才加 join。互斥分支不可能同时到齐，不能接 join。不能以“图看起来完整”为由强行闭合所有分流。
- 普通业务动作多入线默认分别触发动作，不自动同步。来源条件已清晰、读者不会误判时保留原结构；需要强调不等待时才加 merge。若原节点同时处理业务，保留动作，在必要时另加纯汇合，不把动作吞掉。
- 一个节点不兼任多入汇合和多出分流；确需两种职责时拆开。split 推荐一入多出；join/merge 推荐多入一出。结构尚未完成时显示提示，但允许保存草稿。
- 不把“先来者赢”“按条件启动多路后只等实际启动的路”当作 merge 或固定 join；本次不实现竞速或包容汇合。需求命中这些语义时明确待建模。
- 图形采用工作台自定义切角形与可读模式标识，颜色继续表示实现状态，不宣称为严格 BPMN 标准符号。实际图中同一分流的父图概览与子图展开不再次启动一轮业务。

## 评审与校准

1. 分别推演 A 先、B 先、A 失败/跳过、A 与 B 都到达；写清继续几次、等待谁及未决责任。
2. join 的全部入路必须属于同一业务对象、同一执行轮次；不能用两个不同订单或同一路重试凑齐。
3. merge 接资金或设备副作用时核对重复到达保护；“汇合”本身不提供幂等。
4. 完成后保存重读模式，检查画布、属性、SVG 和 Mermaid 语义一致；单元测试不是业务仿真或验收。

本组案例：新单主线与旧单后台两路都执行，且新单不等待后台，因此使用 split，不增加 join。业务结果与消息确认分别推进同理。已有条件明确的共同处理入口保持原动作；没有真实等待全部结果的证据，不为展示 join 能力在业务图造一个。

语义参考（2026-10-30 核对）：[并行网关](https://docs.camunda.io/docs/components/modeler/bpmn/parallel-gateways/)；[互斥汇入的直通语义](https://docs.camunda.io/docs/components/modeler/bpmn/exclusive-gateways/)。仅采用执行关系语义，不套用特定引擎线程或选路实现。

# 从源码到最小改图

用于依据源码绘制和核验业务流程，尤其是异步通知、定时处理、提前返回和异常结果。初次建模时一并核对业务结果和实际承接。

## 源码一致性与业务闭环分开评审

- **先确认评审对象。** 用户先定目标流程、后做实现时，依据目标图的触发、输入输出、状态分流和恢复边界判断方案是否闭环；“待实现”本身不是流程断点。源码用于核对现状与复用条件，实现状态另列，不能因为新承接尚未编码就否定设计。反之，目标图有承接不证明现网已获得保障；只核局部返回与重试时，不扩大宣称整条业务已通过验收。

- **先还原，再判断。** 方法返回、通知成功、异常捕获和局部任务结束只说明技术执行；沿同一业务对象继续核对状态、资金及后续责任。对本次路径的提前返回、未查到对象、跳过和捕获异常分支，也要问退出后原对象由谁处理。准确复刻后仍可能得出“现状不符合产品要求”，不能将源码当作业务验收标准。
- **分清问题来源。** 已有接收/恢复代码却未画出，是建模漏项，补原有关系；源码存在可触发的未决分支且缺少可靠承接，是实现缺陷，保留触发条件与实际后果；尚未查清其他消费者、扫描筛选或调度启用情况，则标证据不足、闭环未获证明，不能直接断言全系统没有兜底。源码缺陷与评审漏判可以同时成立。
- **现状与目标同时可辨。** 现状路径保留“条件→实际动作/返回→未处理后果”，标明不符合目标验收；拟补的检查、异常登记或恢复路径标待实现。不能只补目标线而抹去缺陷证据，也不能因为如实复刻了缺陷就将图判为业务闭环通过。
- **局部结束不自动构成缺陷。** 若业务已可靠移交且正常、失败、超期均有承接，通知任务可以结束，不要求同步等整单完成。没有这些证据时，“仅本次结束”“后台继续”不能作为辩护；也不能改成重复启动、无限重试或无证退款。具体出口检查复用 [产品结果审查](retry-lifecycle.md#从产品结果审查退出口)。
- **交付说明两层结论。** 分别说明图是否忠实、业务是否闭环，以及触发条件、证据和未核实范围。若此前只复刻代码而漏掉产品判断，明确指出评审遗漏；静态可达风险不等于已发生事故，目标图保存不等于业务修复或部署验收。

## 先查当前执行，不先发明机制

- 先读最新图及直接父子图，列清一条具体路径：触发者、业务对象、进入此节点已满足的条件、此处真实动作、结果接收方。先指出用户质疑是否源自入口前提重复、术语不清、源码缺口或图上漏线。
- 用户指出跨图出口冲突时，分别核对保存的执行关联与编辑器的浏览返回记录。浏览历史不证明业务返回；接口调用方也不一定是导航父图。按本次真实调用登记输入、返回结果与调用方接收点，内部节点不得固定跳到外层任意算法来补闭环；调用方决定后续。异步派发先返回登记/受理结果，后台执行与后续事件单独承接，不能返回已结束的原调用。若同一出口同时接同步返回和异步结果，先拆清执行范围，再选形状与关联。
- 依据被调方法、调用者和返回点确认顺序。前置校验通过、HTTP成功响应、业务动作完成是不同结果；业务可能先执行再返回成功。请求失败须按已有证据区分明确未执行与结果未知，不能凭失败或超时断定已执行或未执行。
- “任务”写清是调度作业、持久化通知记录、订单处理记录还是本次方法执行。使用“接管、恢复、预算”前，确认哪个记录、身份、字段、状态、读取入口及责任动作；现有实现没有的只能标方案，不能先提出通用收尾任务再当作已存在机制解释。
- 对定时节点核对实际筛选条件和逐笔执行代码。例如到期通知回扫可能只选可重试记录、锁内比较通知次数；耗尽分支可能来自本次结果处理，而不是下一轮再选中已耗尽通知。注释与代码不一致时按实际代码并标记差异，不凭注释承诺次数/周期。

## 故障原因与模块归属

- 模块归属只说明实现位置。通知执行、依赖读取、结果保存、支付业务拒绝分别按真实失败阶段与证据命名，不能因通知代码位于支付模块，就把通知故障归为支付业务异常；也不能凭异常类名推定网络故障或业务未执行。
- 区分“源码内部可定位的发生位置”与“调用方能识别的输出”。核对真实返回类型、异常传播/包装、持久化字段及调用方条件；内部执行和保存位于不同语句，不等于模块已经返回两类错误。尚无判别字段或契约时，现状保留合并的执行异常结果及其实际后果，细分目标标待实现，不虚构返回枚举。
- 对重试耗尽、执行异常及结果保存异常逐项核对原对象、原次数、事务提交结果与接收前提。耗尽不等于支付失败，HTTP异常不证明业务未执行，保存失败不证明新状态或次数已经提交。只有原持久化记录仍满足真实状态/到期筛选，才能说明可能被再次发现；不能把所有故障无条件交回同一回扫，也不能将记录可查等同于异常已可靠登记。
- 逐条沿出口到接收判断的真实分支及最终结果；错误分类发生在调用方、公共异常登记还是未实现方案，应明确标注。已有分类证据则保留有效细分，不反向把所有异常永久合并。发现同类误用时只核当前主题直接相关流程，并保留原业务原因与后续故障的区别。

## 最小改动并保持事实

- 先比较现有父图/子图是否已承担同一检查和资金防重。复用有效入口和方法，只补缺失的条件、结果或接线；不因一句风险提示新建查询表、调度、通用治理或多张子图。
- 用户删除或收敛节点后，以最新保存版为基线，不恢复已否定方案。删除重复核验时确认其实际保护仍在复用子流程；若删除会使关键未知结果变成无条件资金动作，应明确指出具体断点，不能偷偷删除保护，也不能换名重新长回整组节点。
- 新增核验先明确缺少哪项事实、由谁读取，以及哪些分支需要它。已有可信且足以选路的业务结果，可直接交对应后续；未知、过期快照、读取失败或冲突才接所需复核。不能为统一出口让正常结果强制经过待补异常核验，也不能把布尔成功、通知成功当作已核实业务状态。若确有并发变化风险或新业务规则要求再次检查，应明确依据及失败去向。
- 对失败/未知的必要分流，按真实发生位置和已有结果分类表达；不要在路径末端临时发明一个无法取证的“是否进入业务”判断。确需新增取证时，说明具体证据来源及未实现部分。
- 一个结论只在维护源定义。当前节点说明应给当前口径和方法证据；历史错误保留在版本中，必要历史简短标失效，不反复叠加互相否定的长说明。

## 出口与入口成对验收

凡本次新增、修改或评审涉及入口、出口、公共调用及返回，必须检查对应两端的实际逻辑；不能只核对节点存在、形状一致或链接能打开。先按同一业务对象正向走到接收后的具体分支，再从入口反查这些来源是否都符合前提。

- **出口实际给了什么。** 核对业务身份、状态/结果、原请求、失败原因和持久化结果；技术成功、次数变化、方法返回或局部退出不能补出未取得的业务事实。保存失败不得作为“已保存、等回扫”的输入。
- **入口真的能接什么。** 核对对象范围、状态过滤、时间窗口、次数/期限、记录存在与真实触发；出口结果必须满足这些前提。只扫描某一状态的作业不能接收所有异常，未保存的记录不能靠按任务表回扫恢复。入口不匹配时改接已有适用入口或补明确待实现的核验，不能为了连通伪改原对象状态。
- **接收后究竟走哪条。** 对每类输出指出接收判断的对应条件和后续；公共return按各调用点逐一核映射，独立后台不返回已结束的调用。至少推演本次相关的耗尽、超时、保存失败/未知、记录缺失和执行中但已超期；早退、跳过或“执行中”标志不能绕过期限检查，也不能重开原预算。
- **什么时候可以结束。** 正常推进/真实完成、异常已保存且可见有后续、明确失败返回分别核实。已知原对象的未决结果追到公共异常登记及其保存/可见性判断；登记失败必须向实际调用者或作业明确报错，不能只留日志或宣称已登记。整批读取失败尚无具体对象时明确报告批次失败并保留来源，不能伪造订单异常；未证明后续恢复的，仍记未闭环缺口，不因本轮报错就声称业务已完成。

复杂关系可用一张精简表记录：`源出口及条件 | 原对象与输出事实 | 接收入口及筛选前提 | 对应出边/处理 | 成功、异常保存失败及超时结果 | 证据/待补`。这张表是走查证据，不替代原图路径。交付分别报告结构有效、两端逻辑是否匹配、实现/启用证据与业务验收状态。

## 固定对应标签与逐级反查

**先选接手位置，再配标签。** 把出口已证明的事实逐项代入上层分支。恰好命中一支时，直接关联那条分支的第一个承接节点，保留上层判断供其他来路使用。若几支都可能命中，写清尚缺的字段、证据或调用结果，把出口接到真正作出区分的判断或它必经的取证动作。上层必须执行的写入、通知、记账或独立检查照常保留。结果属于子阶段时逐层承接，事实原样转交就沿用同一个标签。一个出口混装数种已经分开的结果时，从各自已知的位置拆出口。若下层只提供一个粗粒度值，保留这个值，上层按其确实拥有的证据选路。

**使用工作台原生关系和字段。** 普通出口用 `output.target`，有明确来源的输入/事件用 `source`。公共模块用 `call` 和该调用点的 `returns`，核对调用点至本地接收节点的实线。异步派发、回调、定时和已退出后的恢复，关联真正接收的入口及触发条件。导航归属单独保留。在图上标明发送、进入下一阶段和业务完成的不同结果。

| 放在哪里 | 固定格式 |
|---|---|
| 源节点的输出字段、接收节点的输入字段 | 两端同一稳定行 ID `handoff-<英文业务键>`。可见字段名一律为 `【对应】<中文业务事实或触发>`，类型一律为 `流程对应标签`。 |
| 字段含义与条件 | 两端逐字一致。说明里写清对象、已取得的事实和仍未知的结果。标记只用于读图，保留真实业务参数与枚举。行的「来源／取值」列出对端：`流程名 · 节点名 [节点ID]`。同一事实有多个来源时逐条列；模块返回再列实际调用处及其 `[调用节点ID]`。 |
| 一个接收点有多个结果 | 按结果逐行列出。每对原生关系应唯一匹配一个标签。相同事实可以有多个来源，保留每条真实关联。相同后续、不同原因在本次交接仍有意义时，分别起名。 |
| 共享模块、逐级转交 | 每个调用点的接收字段匹配实际返回，保留调用上下文。中间图接收再转出时，分别给入口填写来自上游的标签、给出口填写交给下游的标签。同一事实原样转交可沿用原键，新的事实使用新的键。 |

逐级转交时画成 `甲图出口 → 乙图接收入口 →（乙图内）乙图出口 → 丙图接收位置`。乙图原样转交时，图内一条线就够。若几路交来同一结果，可以共用接收位置，保留每个来源的反查入口。需要分别标明来源或工作台的单一 `source` 无法完整表达时，用带来源名称的入口汇入同一后续。乙图自己的判断得出相同结果时，保留从该分支到乙图出口的本地连线。复核时分别从子图出口正向进入、从上层入口反查，并看读者能否在复制的参数里区分“从哪来”和“交给谁”。

只看高层业务概览时，下一图实际处理结果的动作可以作为承接位置。读者要求沿每个出口进入对方输入、逐项走查或从接收处反查时，使用显式入口模式。普通动作、判断、调用和终点前画一个标明来源的 `input`，以本图连线接回原业务位置。常规图的 `input.source` 只关联一个源节点。逐源反查时可设并列接收入口，让同结果的来路汇入本图同一处理。真实定时、消息、响应或人工事件本身就是接收位置，区分上游交接的对象和实际触发者。公共模块入口依本次调用上下文接收，靠实际调用／返回映射或入向 `output.target`、成对标签定位来源。用 `pair_labels.py --explicit-inputs` 检查全部原生出口及其接收类型，再验证每个新入口之后的第一项业务处理、带来源的复制块和定时触发边界。例如“订单已完成，退款实退待核”可直接接上层同名结果。若只知道“订单与资金均核平”，而正常或异常结束还取决于订单记录的结束原因，应接“已记录的结束类型？”；标签含义写明待区分的字段。若当前调用只拿到布尔成功，则保留调用者真实可见的信息，不能利用制图者知道的模块内部分支新增代码没有的动作。拟议处理、缺少证据和真实业务测试的状态分别沿用本图既有标记。

改过目标或返回映射后，用旧节点 ID、旧名称和“全部返回／统一判断”等原措辞检索本主题的节点说明、连线说明和既有参数。把旧去向换成当前口径，保留源码和测试依据；可由原文确认归属的失联说明重挂到实际节点。收敛旧判断后复查它的入线和旧出边，避免留下另一条仍可误读的路径。

从上层分支选择“查看来源”追到实际产生事实的出口，再正向核对一次。模块从实际调用点进入，用“返回本次调用结果”核对；多个调用点逐个走。用 `python3 scripts/pair_labels.py <CLI草稿> [另一个关联主题草稿 ...]` 在草稿和保存回读上检查成对字段、遗漏和脱节的旧标签。加 `--at 流程ID 节点ID` 查看指定节点的双向清单。缺外部主题时补拉后检查。脚本核对图上声明；对每个仍接判断的出口，仍需验证其余选项是否可能、必要动作是否保留。全主题走查时也检查每个模块返回、分支终止及根本没有画出跨图关系的结果；结构检查通过后另报业务测试事实。

## 从出口走到终点，并追踪原因

- 每次修改子图输出，同时核对父图接收节点、对应结果出边及后续。`target`能跳转但父调用结果没有承接线，仍是图上断点。同步调用返回、独立定时查询和同次调用展开应分别表达。
- 已确定的业务结果直接交到上一层对应分支；仅当还缺会改变选路的具体事实时接真实判断，并写清缺什么、由谁读取。组合输出包含多个已知且去向不同的结果时，按有据的实际产生点拆出口或 return，逐调用点更新映射与实体出边；不能在末端新增一个无法取证的泛化判断，也不能把公共 return 写成固定父图目标。
- 跨图输出保留决定下一步的具体结果。知识库投稿的已发布、审核退回、发布未决分别进入文章展示、作者修订、原任务查询。已有明确对应的出口时复用它。
- 逐个输出回答“到接收图后走哪条边，依据是什么”。父图确实负责统一分流时可以保留判断，但输入结果与对应出边要一致、可辨认；不能强制全部绕过父图。只知道状态已变化却未核实具体结果时，接真实的结果复核/异常路径，不擅自选成功；不复制已有检查来弥补命名不清。公共模块继续按各调用点返回映射处理，不改成固定父图出口。
- 发布流程可逐步推演审核状态未保存、发布成功、原发布任务未决和结果查询失败。按当前证据判断每条路线的责任人和后续入口。
- 分开稿件状态与任务执行状态。审核通过后，发布任务可以仍在等待结果。终点名称写清结束的是本次查询、发布任务还是整个投稿流程。
- 追踪原因从异常入口、持久化记录和后续查询到最终展示的传递。保存原始业务原因，后续查询错误另行表达。核对字段、枚举及覆盖位置，缺少源码映射的内容标待确认。
- 交付区分：原图保存及有限路径走查、源码已实现能力、仍需接入的目标方案、真实业务验收。只验证受影响图及路径，发现新证据才扩大范围；结构保存、缩略图和聊天解释不能替代可读画布核对。

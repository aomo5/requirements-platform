# 流程建模与评审规范

适用于业务流程的绘制、结构修改与评审。主框架选用 **bpmn-io/bpmnlint 的规则化检查方式**，执行语义依据 **OMG BPMN 2.0.2**，结合当前工作台作有边界的简化。这里的规则用于画对、读懂和核验流程，不使业务系统自动获得工作流引擎能力。

## 1. 来源、选择与适用层次

资料核对：2026-10-30。以下是官方标准或维护者一手资料；GitHub `main` 与文档可能变化，今后更新规则时重新核对相关项，不要求每次画图联网。

| 候选 | 采用判断 |
|---|---|
| [bpmn-io/bpmnlint](https://github.com/bpmn-io/bpmnlint) | 主参考：提供命名、分叉、汇合、结束、连接和重叠等规则及正反例，适合转为绘图验收项 |
| [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/) | 语义依据；标准不等于所有推荐布局风格 |
| [bpmn-io/bpmn-js](https://github.com/bpmn-io/bpmn-js) | 标准建模与渲染实现参考；本次借鉴规范不要求替换工作台 |
| [bpmn-js-token-simulation](https://github.com/bpmn-io/bpmn-js-token-simulation) | 借鉴“让执行路径实际走一遍”的验证方法；只有真实运行过才能称仿真 |
| [Mermaid](https://github.com/mermaid-js/mermaid)、[draw.io](https://github.com/jgraph/drawio) | 分别擅长文本绘图与通用图形编辑；不以绘制成功代替业务语义审查 |

“最适合当前任务”是按业务语义覆盖、规则可核验、正反例与工具适配作出的选择，不作全 GitHub 客观最优或按 stars 排名的声明。

区分三层要求：**标准语义**决定一条线意味着什么；**本地可读性约定**要求把隐含关系画清楚；**业务证据**决定实际应该走哪条。比如 BPMN 允许某些隐式行为，而我们为减少歧义优先显式分流；不能声称所有普通任务多出线在 BPMN 中都非法。

## 2. 先选对图的职责

- 业务流程图回答动作、条件、责任与后续；状态图回答同一对象允许的状态变化；时序图回答调用与消息先后。不要在一张业务主图里同时塞入全部状态矩阵、调用栈和消息协议。
- 每张图明确对象与范围，例如“文章从投稿到发布”或“本轮过期审核扫描”。同一页面中的多个独立入口必须有各自触发源。
- 节点保持同一抽象层级：总览表达业务阶段及结果，详细图表达单一动作或判断。详细处理中的“检查、发布、重试、完成”混在一个方块时先拆职责；不要机械按每个方法拆图。
- 总览使用清楚的业务阶段名称；详细步骤采用“动词＋业务对象”，判断采用明确问题，出口写条件或结果。节点 ID、代码方法、SQL、版本证据放说明，除非本图本来面向研发细节核对。

### 业务总览与阶段展开

先确定读者需要回答的问题。业务总览回答“同一业务对象经历哪些阶段、何时进入下一阶段、哪里可能等待或失败”；阶段图回答“这一阶段怎样处理并得到结果”；诊断图回答“哪项具体检查导致问题、之后实际走向哪里”。简单业务可以一图完成，复杂业务按需要逐层展开，不规定统一层数或节点上限。总览围绕业务生命周期组织，例如提交草稿、编辑审核、发布文章。源码调用关系用来核实阶段内部的实现，不能代替业务总览的组织方式。

| 关系 | 在图中表达什么 | 不能推导什么 |
|---|---|---|
| 阶段展开 | 同一业务阶段的概览与详细处理，输入条件和阶段结果相互对应 | 有展开图不表示父图发起一次同步方法调用，也不重复开始业务 |
| 公共模块调用 | 此处引用一份公共定义，按本次调用的输入与结果返回当前调用点 | 被某阶段调用不改变模块归属；同一模块不复制多份 |
| 独立后台 | 由消息、定时或人工等真实来源独立触发，关联原对象并有结果接收方 | 导航放在某阶段下面不表示该阶段等待后台完成，也不伪装同步返回 |

总览的阶段节点可以代表跨多次事件、查询或执行的业务过程；这种阶段不能因为有子图就标为 `call`。只有确实表示一次调用且有本次返回契约时，才使用公共模块调用节点。阶段之间的箭头表达业务推进条件，不必逐条对应程序调用；展开后仍须区分同步动作、异步事件和等待。导航中的分组、`parent` 归属和点击展开只组织阅读，不能作为调用或等待关系的证据。

问题诊断按层级承接：总览保留影响阶段结果的风险条件、未决或失败结果及责任去向，相关详细图保留全部必要检查、失败/未知分支与真实后果，并有明确入口。例如总览显示“发布结果未确认 → 继续核对同一投稿”，详细图再展开任务登记、结果查询和恢复条件。用户直接评审某一具体故障时，以对应详细图为当前评审面，不把该故障的关键检查折叠到不可发现的位置。

概念参考（2026-11-03）：[SAP Signavio 流程层级](https://www.signavio.com/wiki/process-discovery/business-process-mapping-levels/)用于按读者和目的分层；[嵌入式子流程](https://docs.camunda.io/docs/components/modeler/bpmn/embedded-subprocesses/)与[调用活动](https://docs.camunda.io/docs/components/modeler/bpmn/call-activities/)用于区分内部展开和独立复用；[可读流程模型](https://docs.camunda.io/docs/components/best-practices/modeling/creating-readable-process-models/)用于保持清楚的业务命名与路径。本工作台只吸收这些建模概念，不套用 Camunda 的实例、变量、事务或执行器行为，也不把导航子图宣称为完整 BPMN 子流程。

### 模块定义与调用

按业务责任、输入和结果边界划分模块，参考源码已有封装与真实调用，不机械按方法、泳道或节点数量拆图。归属方便组织定义；同步调用等待本次结果返回当前调用点；独立异步由明确任务或事件触发，结果由指定接收方承接。函数封装不证明调用已异步或不阻塞。

同一语义的公共定义只维护一份，由多个调用点引用。每处调用明确输入对象、目标入口、输出结果及本图返回位置；公共定义输出结果，由调用方决定后续。不要复制内部实现模拟复用，也不要把公共返回固定到一个父图。职责、输入或副作用不同的流程不能只因名称相近就合并，例如发布阶段包含稿件校验、发布和结果保存，校验模块只承接其中的检查。

模块中只保留本次调用的范围。独立定时、人工恢复或异步回调应在各自入口调用模块，不能让没有原调用上下文的事件走“返回调用方”；返回受理结果与后台业务最终结果分别表达。调用与返回导航只辅助阅读，不代表运行了业务或仿真。

业务总览按阶段推进，保留影响阶段结果的风险边界及承接；公共调用位于实际使用它的阶段，算法和恢复明细在相应模块展开。内部检查是本轮问题时，展开图必须保留检查、失败和未知分支，总览保留其业务影响与承接；不以“处理异常”或节点说明替代问题路径，也不把全部内部判断再复制一份到总览。

### 连续处理段去重

本地可读性约定：发现重复结果判断时，向前检查到最早相同动作或调用，而非只删最后一层重复。比较输入契约、目标入口、分支条件、动作与副作用、结果去向，以及事务、执行责任和重试预算；仅触发来源不同且进入后的处理一致时，保留各自来源与必要准备步骤，共用后续连续处理段。例如首次通知与到期通知均调用同一入口且五类结果处理一致，可在调用处收敛。

“返回当前调用方”约束本次执行的上下文，不要求每个来源都画一套调用和判断。共用节点表示每次到达各自执行：沿用该次原对象、读取次数、来源及批次上下文，不等另一来源、不合并数据、不重开预算；已有锁、幂等及批次完成责任保留。若必须等多个结果到齐，应按真实同步另建模。参数契约、事务边界、责任、策略或结果承接有差异时保留差异段，不能仅凭节点同名强行合并。

修改时同步迁移入线、调用返回映射、结果出线、跨图引用及说明；选一组稳定 ID 保留，去掉失效的“每个来源必须独立画一份”说明。按每个来源和每类结果走查，确认结果仍进入正确处理，没有因合并变成等待、重复调用或漏掉异常。此项只验证图定义，不能把节点变少报告成实际任务执行次数变少。

## 3. 基本语义与当前工作台表达

| 关系 | 正确语义 | 工作台简化表达 |
|---|---|---|
| 顺序 | 前一步达到约定完成条件才继续 | 有向连线；不能用来仅表示“有关联” |
| 条件择一（XOR） | 一次只走一个结果 | 判断节点＋明确互斥条件；必要时默认/未知出口 |
| 并行分流（AND） | 所有出路都被激活，不检查选路条件 | 专用并行网关优先；不支持时用单独“并行分流·全部执行”节点，各路编号并分区，不与业务处理混在一个方块 |
| 等待全部（AND 汇合） | 所需各路到齐才继续一次 | 专用汇合网关或明确“等待 A、B 均完成”节点；核对所有分支都能抵达 |
| 互斥汇入 | 备选路径到达即可继续，不等另一条 | 明确择一语义；不能拿它同步并发路径 |
| 条件多选（OR） | 满足条件的多条分支可同时执行 | 明确标多选与等待哪些已激活分支；只有确有需求才使用，不为简图伪装成 XOR/AND |
| 事件竞争 | 等待多个事件，先到者决定路径 | 显式等待及各触发事件，说明另一路是否取消；不要当成普通数据判断 |
| 独立异步 | 发送与接收分别执行，后者不随发送动作自动完成 | 显式“发送/登记”与“收到事件/任务到期”入口，关联同一对象；标是否等确认、等结果 |
| 跨图继续 | 当前视图结束，业务路径继续 | 有名称的输出/接收映射和父图真实后续；不是随手加一个终点 |
| 局部结束 | 当前支路或执行范围结束 | 结束节点写范围与结果；其他活动路径继续可见 |
| 全范围终止 | 取消指定范围内其他活动路径 | 仅有真实取消语义才使用；当前工具无专用标记时写明范围及取消对象，不能用普通结束形状暗示 |

依据：[并行网关](https://docs.camunda.io/docs/components/modeler/bpmn/parallel-gateways/)、[互斥网关](https://docs.camunda.io/docs/components/modeler/bpmn/exclusive-gateways/)、[普通结束](https://docs.camunda.io/docs/components/modeler/bpmn/none-events/)、[BPMN 符号与关系](https://camunda.com/bpmn/reference/)。不要将特定引擎的线程、XML 选路顺序或运行配置强加到本项目源码。

### 结束点的判定顺序

1. 确认结束的对象和执行范围：支路、子流程、一次批次还是全部业务。
2. 检查该范围是否还有活动、等待或未处理责任；普通支路结束不会自动取消其他支路，全部完成也不能仅看其中一个终点。
3. 如父流程仍须继续，核对子流程结果在父图的接收节点与后续线。**合法的子流程结束事件可以返回父流程**，不是全业务结束；标准 BPMN 不从结束事件直接再拉顺序流。
4. 工作台的“子图”若只是导航展开，不等同于 BPMN 同步子流程。早期主线继续、后台仍运行时，可用成对跨图输出，明确它们是同一分流的展开；不能让父图误读成等整个子图完成。
5. “无记录/无需处理/已接管/待确认”先判断其业务含义；不要机械改成“完成”，也不要为了消除终点强行连接到与它无因果依赖的下一步。

依据：[end-event-required](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/end-event-required.md)、[no-implicit-end](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-implicit-end.md)、[superfluous-termination](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/superfluous-termination.md)。这些规则要求真实终止清楚可见，不要求把所有中间输出都变成业务终态。

## 4. 可检查规则

下表是本工作台评审门槛；不是声称直接运行了 BPMN XML 检查器。规则命名参考 [bpmnlint 推荐配置](https://github.com/bpmn-io/bpmnlint/blob/main/config/recommended.js)，具体采用范围由本地规则明确。

| 检查项 | 检查方法与修正方向 | 来源性质 |
|---|---|---|
| 显式分流 | 多出边逐一说明是择一、全部、条件多选还是事件触发；禁止“看箭头自己猜” | 借鉴 [no-implicit-split](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-implicit-split.md) 的可读性要求 |
| 无假汇合 | 多条并发线接到普通任务不会自动成为“只执行一次”；需等全部时显式同步，且不能漏一条导致永久等待 | 借鉴 [fake-join](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/fake-join.md) |
| 拆开汇入与分出 | 一个复杂节点同时多入多出时分开同步与选路职责，避免不可辨认的网关 | 借鉴 [no-gateway-join-fork](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-gateway-join-fork.md) |
| 分支条件完整 | 条件能实际判定；择一条件优先互斥，不能依赖画布顺序；未知和读取失败按需要独立处理，不能默认为“无” | 借鉴 [conditional-flows](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/conditional-flows.md) 并作业务扩展 |
| 起点有来源、出口有去向 | 按独立入口追踪；非终态无出边需核实是否跨图输出、等待或漏线，不能为了过检查随便加结束 | 借鉴 start/end-required、no-implicit-start/end |
| 无悬空与误重复 | 检查连接两端存在、无遗留孤立节点；同对象同条件重复边可能多启动一次。不同条件的同端点边不能机械去重 | 借鉴 [no-disconnected](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-disconnected.md)、[no-duplicate-sequence-flows](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-duplicate-sequence-flows.md) |
| 名称可判读 | 任务、事件、结果有业务名称；判断的出线说明条件。无需给每条普通顺序线填重复说明 | 借鉴 [label-required](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/label-required.md)，保留本地简洁偏好 |
| 父子结果一致 | 按来源、对象、条件、结果逐项对照父图接收及后续；检查返回后是否重复发布 | 本地业务核验规则 |
| 异步责任不断 | 区分发送、接管、结果与超时；原请求未知不自动重发。画出接收、关联与恢复依据 | 消息语义＋本地可靠性规则 |
| 结束范围正确 | 普通局部结束不假装全局终止；真实取消不能仅命名“异常结束”；返回父流程仍有承接 | BPMN 作用域语义＋本地可读性规则 |
| 循环可退出/可恢复 | 每次回边有触发、预算和退出条件；已退出执行不被画成无条件立即自循环 | 本地异步核验规则，见原有循环参考 |
| 无语义遮挡 | 关键条件、箭头和节点边界可读；长线不能穿过无关节点或伪装连接 | 借鉴 [no-overlapping-elements](https://github.com/bpmn-io/bpmnlint/blob/main/docs/rules/no-overlapping-elements.md)，布局为本地约定 |

模型存在错误对象、漏接结果、假完成、重复副作用、错误同步或无恢复等待时，不能判“流程闭环通过”。未能确认的业务事实标待核实；不补造事实求图形完整。可读性问题若影响分支/结束理解，也属于本次必须修正的问题，而非可忽略的美观项。

## 5. 并行与异步的两个常见结构

绘图与评审的模式选择及改图边界见 [并行分流与汇合](parallel-merge.md)。

**同一业务实例内两路并发：** 显式分流 → A、B 各自执行；需要共同结果才显式汇合。A 可以在本支路结束，B 继续。不能把 A 的普通结束当成取消 B，也不要求所有分叉必须重新汇合。

**独立后台任务：** 主线的触发/可靠交接阶段 → 主线后续；后台由接收任务/消息或独立调度进入 → 后台结果。若发送失败也不得阻塞主线，必须有相应隔离和恢复依据，不能只靠画一个 AND 网关声称已经解耦。两个独立实例间的通信不是同一实例内的顺序流。

严格 BPMN 中，顺序流用于同一流程的执行顺序，消息流表达参与者间通信；泳道不等于独立进程或线程。当前工作台的背景泳道只辅助责任分区，是否异步仍以实际触发与执行边界为准。[消息事件](https://docs.camunda.io/docs/components/modeler/bpmn/message-events/)

### 派生接收与父子入口一致性

父图一个业务输入展开到子图后，出现多个起点形状不自动是错误。逐一判定：父图传入的业务、该次分流发送消息后的接收、真实独立定时或人工恢复。不能把派生接收漏画成无来源的第二业务入口，也不能为凑成单入口删掉真实恢复路径。

- 对派生接收，画出“父图业务输入 → 分流 → 发送动作 → 异步交付 → 对应接收 → 后台处理”。关联对象、发送/接收边界与是否等待必须在可读局部画布中可辨认。当前工具可用带明确“异步消息送达”标签的连接表达因果承接，但不能冒充同线程顺序执行；严格 BPMN 跨参与者须用消息流。
- 父图分流与子图分流属于同一动作的概览和展开。逐路对齐来源、动作、输出及父图接收，不因展开再启动一次后台任务。原生接收节点形状按工具能力和语义选择，不制定“接收一律改步骤”的规则。
- 发送成功、消息实际到达、可靠接管和业务完成分开判断。消息延迟不阻塞已独立推进的主线；投递失败/未知按已确认机制保留责任和恢复入口，不凭空新增队列、补偿平台或可靠性承诺。
- 同步调用返回也要配对：调用来源、返回点及原调用关联应连续可追踪。不能把同步返回画成独立消息入口，不能为了补一条线新增业务并行执行或让业务重做。
- 跨图入口的 `source` / 跨图出口的 `target` 是跨图导航与承接关联，不自动代表本图内的执行顺序。仅当两节点确实在同一执行实例中前后发生、且对象与条件一致时，才画图内顺序连线；否则保留来源/目标关联，删除会把不同分支或不同调用混成上下游的连线。尤其要区分“业务处理输出”与“原调用返回入口”：不能只因两者在同一张子图、名称相关或可互相跳转，就把它们相连。

读图检查：遮住侧栏说明，从每个接收节点逆向指出发送者/调用者，再正向追到接收后的动作；父子图各走一遍，确认是同一次触发，且独立恢复不依赖主线再次执行。对每条跨图节点之间的图内连线，再核对它表达的真实先后关系；导航关联不能替代执行证据。

### 恢复条件必须有真实触发来源

“依赖恢复后”不是完整的事件或恢复机制。先分开**触发源**（谁再次启动一次检查）与**进入条件**（这次是否允许继续），再画清以下链路：

`定时到期／收到明确事件／人工发起 → 检查哪个依赖或原任务 → 判断本次结果 → 接收节点或本次退出`

- 明确具体依赖，例如数据库查询、Redis 锁、外部业务接口或调度器；不同依赖在不同阶段检验，不笼统合成“系统恢复”。
- 说明谁检查、由哪个入口触发、用什么结果判断可继续。若源码是下一次业务查询/请求成功才继续，就直接画该动作及成功/失败出口；不能臆造独立的健康探测器或“恢复通知”。
- 定时扫描场景：失败执行结束后，原持久化任务留存；独立定时入口按已确认配置触发查询。扫描成功且任务满足状态/时间条件才进入原任务核验；扫描失败不能当作无候选。不从结束节点拉顺序线去触发下一轮调度。
- 明确调度器自身不可用的边界：任务执行器要运行且任务启用，才有下一次周期触发；若调度暂停、服务未恢复，依赖自然可用不会自动证明业务重启。实际恢复责任/动作未知时标待核实，不虚构已完成的运维操作。
- **流程方案可以设计新的调度作业，但定时入口不能凭空出现。** 在目标图中明确作业由哪个服务/模块负责、在哪个生命周期阶段产生或注册（例如后台实例启动且作业启用时），并明确注册后按什么周期配置或到期条件触发每一轮处理。周期事件表示“一轮处理现在被触发”，不表示每轮都重新注册作业。作业注册属于调度机制的生命周期；若本图范围不包含服务启动，就在定时事件名称/说明中指出外部作业来源，再把事件连到本轮扫描动作，不必虚构一个业务步骤作为上游。只有启动注册及注册失败本身属于本图范围时，才把它展开为流程步骤和分支。
- 现状图依据源码确认真实的 Job 注册方式、启用条件、周期配置、查询范围和职责；目标图可以提出新增作业。对照现有 Job 是为了判断职责能否复用，不要求目标方案先在代码中已有实现。名字相近或同属后台定时任务不证明职责相同；例如只轮询已持久化任务的 Job，不能替代发现尚未建任务对象的补扫。新方案的模块/代码位置应标为建议，不得写成现有实现。
- 注册阶段、启用配置、周期/cron、批次策略或执行器归属仍未决定时，把缺项明确列为待确认；流程可以先定义入口和处理逻辑，但不伪称具体参数或代码已经确定，并为后续开发留下责任模块及决策映射。
- 回调场景标事件发送者、接收入口与对象关联；人工场景标角色、操作入口与操作后检查。无需为每次条件变更新增平台或监控系统。
- 图上保留能看懂的触发入口、检查动作、成功和未恢复出口；说明中保存具体方法/状态/时间依据。不能只在一条回边上写“恢复后”就判闭环。

## 6. 分层与布局

以下是本地可读性约定，不宣称为 OMG 强制几何规则。

- 步骤方块统一使用直角矩形；开始/结束与判断保持可辨认的语义形状，不把所有符号都改成方块。该偏好适用于本工作台简化流程图；若另有严格 BPMN 交付要求，应采用其标准活动符号，不能称直角是 BPMN 的要求。

- 主干选择从上到下或从左到右并保持一致；正常后续放主轴，异常和后台分支移到侧面。回边走外围并标触发条件，避免横穿整条主线。
- 并行分流后各路并排且有清晰入口；一支结束时，另一支的后续应在同一局部视图可辨认。标题、编号或泳道辅助识别，不能只靠颜色。
- 按责任或执行范围划分区域，不按任意节点数量分区。不要把“默认/异常/待实现”等证据状态当作角色泳道。
- 主图保持业务阶段这一层级，保留推进条件、风险边界、等待和异常承接；具体算法、查询和重试路径在阶段或诊断图展开，源码证据留说明。拆图后保留来源与结果映射，不把复杂性藏成无去向的“处理异常”，也不按代码调用树堆积总览。
- 节点、标签、箭头不互相遮挡；条件贴近对应出线，交叉处不能看起来像汇合。优先移动节点、调整路径和分层，不靠不断缩小字体解决。
- 在实际工作台检查“全图可定位、局部可阅读”两种视图。只在适应全图的极小缩放截图不能证明可读；只裁正常路径也不能掩盖错误异常分支。
- 不制定与页面无关的统一最大节点数、像素间距或字体值；按当前画布和读者验证。当前工具的节点/边数量上限属于实现约束，不是最佳实践目标。

局部结束、结果分支和回查布局的具体画法见 [可读性正反例与读图验收](readability-examples.md)。按主轴、职责分区、就近结果与外围回查组织相关路径。

## 7. 工具能力适配

需求平台支持公共模块定义、调用节点及返回节点；归属子图与调用关系分离，调用点维护模块入口和逐结果返回映射。原有开始、步骤、判断、并行/汇合、跨图入口、事件、结束、跨图出口、泳道、关联子图及版本保存继续使用；事件支持消息、定时、人工和响应的简化标识及触发/继续阶段，结束支持明确范围；不支持完整 BPMN 网关、完整事件模型和执行仿真。实际操作前仍以当前实现为准。

- 优先使用原生符号。使用 gateway 的 split/join/merge 模式明确全部执行、等待全部和每次到达即继续；出路明确执行范围；若只是异步提示，更准确地写异步触发，不强称为同一实例 AND。不要把普通判断菱形冒充标准并行网关。
- 颜色/虚实已用于现状与目标方案，不能复用为唯一的通信语义。严格 BPMN 的消息虚线与本地蓝色拟优化虚线不是同一含义。
- 子图输出的指向既要有可见业务名称，也要能在父图找到相应真实后续。工作台导航只是定位，不能冒充执行连线。
- 修改前核实当前原生数据及 CLI 是否支持所需调用关系。只有单一父节点、固定出口或导航链接时，不能仅改文字宣称多调用方返回已完成；列明具体能力缺口。能力建设须在用户授权范围内，不能因采用本规范自动扩建编辑器。
- 公共模块的 `call` / `return` 及 `flow.kind` 必须随 CLI、存储、读取和导出保留；逐处核对输出映射和调用方真实后续。既有 `output.target` 仍表示明确的跨图移交，不能当作任意调用者的动态返回。数据契约见 [工作台维护](workbench.md#公共模块与调用数据)。
- 公共定时流程统一使用跨图出口与 `output.target` 关联；定时触发及等待/筛选规则在公共流程内部体现，不新增专用恢复节点或调用处等待模式。关联不表示立即启动调度，见 [公共定时入口的统一表达](retry-lifecycle.md#公共定时入口的统一表达)。
- Mermaid 在这里是受限导入/编辑格式。它能解析不等于模型语义正确；不能输入当前解析器不支持的网关/样式后声称已保存。变更端点若工具会重建边 ID，先核对边说明和引用，必要时迁移；节点 ID 和用户内容继续保留。
- bpmnlint 需要 BPMN 模型，不能对当前 JSON 执行后假称通过；没有真实 BPMN 导出与仿真环境时，执行有记录的人工路径推演。工具缺少关键表达能力时列为单独改进项，不擅自改编辑器或更换平台。

## 8. 交付前走查

针对本次改动选最少且足够的路径：正常、关键失败、未知；涉及并行则交换先后顺序，涉及恢复则加一次退出后再次进入。按“入口 → 激活哪些路 → 等待什么 → 输出到谁 → 完成范围”走图，核对无丢失、重复执行和永久等待。

结构走查与读图检查分别记录“通过 / 需调整 / 待核实 / 不适用”，附具体节点或路径；无需为每个小改生成一份大报告。结构通过但仍需侧栏或口头解释才能辨认关键后续时，读图检查记“需调整”。只有作者自查时如实标明，不声称完成独立读者验收，也不强制每次另找人或另开代理。通过表示当前范围的模型审查通过，既不替代源码真实性，也不替代实际业务验收。规范变更时另用 [规范校准场景](review-cases.md) 防止误规则回归。


## 跨图出口

- 本工作台用右侧尖角出口形表示跨图继续（自定义约定，不宣称是 BPMN 标准符号）。`output` 表示当前支路关联到其他图承接，不能据此推断其他并行支路已结束；目标为公共定时入口时，何时执行由目标内部触发与筛选逻辑决定，不因出口形状就变为立即调用。
- 节点名称写业务结果，如“新单继续启动”；结构化 `target` 保存 `entryPath / flowId / nodeId`。属性面板显示承接节点并提供“前往承接节点”。不以文字箭头、流程名称或返回导航代替业务承接。
- 初稿绘制先确定出口和目标，再接本图上游与父图对应出边。父图已经有准确承接时复用，不额外制造业务入口或再次并行分流。
- 真正完成某个子流程/后台任务仍可使用局部结束节点，并明确结束范围；禁止一律把子流程结束改成出口。
- 尚未确定目标可保留“待关联”草稿，但不能通过完整性评审。目标删除或不可用必须显式提示，不能静默跳到图首页并宣称返回成功。
- 验收：从本图上游读到出口，能跳转定位目标节点，再返回原图；确认目标条件、对象与状态一致，且后台支路不被误判为已结束。保存后重新读取，验证目标字段未丢失；Mermaid、SVG 导出也要保留出口语义。

校准案例：`review/approved` 表示审核通过后移交到 `publish/entry`。独立通知任务可以继续处理。

绘图和评审涉及起点、接收或结束时，统一使用 [入口、事件与结束范围](node-semantics.md) 的节点选择、结构化属性和校准案例。

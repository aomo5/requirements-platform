# 异常传播与执行退出复核

用于订单、消息消费者或批处理共享执行资源，且一笔异常可能拖住其他对象的场景。只评审当前授权链路，不将案例结论套用成全系统缺陷。

## 从内部保护追到外部影响

以生产事件和具体调用栈为起点，核对当前版本的方法及调用方。至少追到实际负责返回、提交、确认消息、释放锁或调度下一笔的位置。重点看正常业务之前的查询、幂等检查、身份/财务核验，以及异常分支中的隔离发布、异常写库、重排任务和锁释放；它们抛错同样可能逃到外层。

对每个实质风险记录：触发条件、异常类型及是否被包装、调用者的分类方式、资金或设备副作用是否已开始/结果是否未知、影响范围（单订单/端口/分片/共享消费者/线程池）、源消息或任务如何保留、下一笔如何继续、实现版本与证据等级。源码可达风险、现场已发生事实和待实现方案分别表述，不把推演说成现场已发生。

## 按执行结果区分出口

- 明确的单笔数据矛盾：保留原文、对象关联和待处理责任；可靠隔离/保存确认后才允许确认源消息并结束本次处理。保存失败或确认未知需要保留源消息和恢复依据，不能为保证流畅直接丢弃。无法关联订单时保留消息、设备及待匹配原因，不虚构订单编号。
- 已识别依赖不可用：保留源消息或持久化任务，说明退避、执行预算、恢复条件和告警。共享依赖确实不可用时不能承诺其他业务立即继续；恢复后先核幂等和原请求。不要把“业务还没开始”或普通 RuntimeException 自动等同于网络故障。
- 副作用已发生或未知：保留幂等、原退款/设备请求身份和已有资金证据；先查询与核账，不重新创建资金动作。设备协议确认与MQ消息确认分别画，确认丢失不能触发重复结算。
- 后台批次及同步新单入口：检查单笔是否会中断扫描、线程池是否拒绝、锁等待是否有界、失败记录/重排/释放再次抛错是否逃逸。只释放自身拥有且已结束执行的锁/租约；超时不证明原工作停止，不允许重叠接管未明资金操作。游标推进不能永久跳过失败项。
- 在线状态与账务隔离：如有独立保活能力，只能用可信接收时间的新鲜上报更新在线，不复用旧积压伪造在线、不触发退款或设备控制；账单及计量证据继续保留。开关、部署和故障依赖范围须据实注明。

## 必须在图上可读

将关键异常直接从实际发生阶段连出：前置核验失败 → 分类；单笔异常 → 可靠保存判断 → 退出当前执行/继续后续；保存失败或依赖故障 → 受控恢复；资金未知 → 独立核验原请求；原请求确认失败 → 只恢复确认。不要只在注释写“可重试/转人工”，图上却无条件返回原消费者无限循环。

保持业务等待与线程等待的区别：订单可以留在未决状态，消费者应在可靠转交后退出；既有10分钟、重试次数等参数只有在本项目确认时才沿用，不写成技能全局常量。按用户要求沿用颜色与现有子流程，保留稳定ID和返回导航。

## 通过标准与知识归属

源码评审与方案阶段只检查相称的图结构和实际渲染，不执行生产退款、清队列或调度恢复。实施验收再按风险选择：异常A之后同设备与不同设备的消息B仍推进；隔离保存失败不丢消息；业务完成但确认丢失不重复资金动作；无效/过期心跳不伪造在线；单笔批处理失败不丢候选；共享依赖恢复后限流继续。不是每次都强制运行全部场景。

技能保存通用判断方法；项目关联资料保存带日期的原始现象、版本、调用栈、受影响范围、源码锚点、证据等级、处理边界、待验证项及对应图/节点入口。不得把具体服务器、账号、凭据或某一订单的财务结论复制成通用技能规则。修复已提交、单测通过、已部署、现场恢复须分开记录。

# 任务拆分

将一份已经写清楚的需求，整理成研发、联调、测试都能直接消费的任务清单，而不是直接跳进代码实现。

## 工作方式

先判断用户要的是哪一种：

- 基于现有 PRD 拆研发任务
- 评审一份已经写好的任务拆分文档
- 结合当前仓库，把偏产品化的拆分改成代码感知型拆分
- 输出正式的 `{功能名称}-任务拆分.md` 文档

默认把 PRD 视为需求事实来源。但如果仓库现状已经体现出明显约束、已有实现路径或兼容包袱，必须把这些约束反映到任务拆分里，不能只复述 PRD。

如果需求涉及前后端协作、页面列表/表单/导出、字段新增、枚举、错误码、金额口径或 Mock 数据，任务拆分前应优先使用 `$interface-contract` 生成或更新 `接口契约.md`。如果尚未确认接口契约，任务拆分中必须补 `T0 接口契约评审与 Mock 确认`，并让后续前端、后端、联调任务依赖 T0。

在当前需求工作台，任务引用设计模块的稳定页面 ID 和当前说明，不另建页面清单或单页规格。页面说明先于画板时使用设计目录中的待设计页；原型任务完成后补同一页面，避免出现说明和画板两套维护源。

## 默认流程

### 1. 先读需求，提炼可交付单元

至少提炼出：

- 核心业务目标
- 范围内场景
- 验收标准
- 统计或展示影响
- 历史兼容与生效规则

拆任务时优先按“可交付单元”拆，而不是只按技术层次拆。一个好的任务，通常对应一个用户可感知行为，或一段完整后端流程。

### 2. 先看仓库，再做拆分

拆分前必须结合代码仓库确认：

- 现有模块和服务中，哪些已经覆盖该流程
- 候选 controller、service、mapper、job、VO/DTO 在哪里
- 现有统计、报表、后台查询链路在哪里
- 当前测试覆盖是否薄弱
- 当前仓库是否包含前端工程或仅包含后端
- `docs/requirements/` 下是否已有同类文档或命名规范

任务描述写清要调整的现有入口、方法和业务结果。例如在能定位源码时，指出由哪个审核方法保存退回原因，以及编辑提交后如何回读结果。

### 3. 采用两层拆分

默认使用两层拆分方式：

- **第一层：按业务交付单元拆**
  - 例如：计算规则改造、订单流程接入、统计口径调整、后台展示、生效范围、测试回归
- **第二层：按任务类型打标**
  - `原型`
  - `前端`
  - `后端`
  - `联调`
  - `测试`
  - `上线`

不要反过来一上来只按“前端任务、后端任务”硬拆。否则任务容易失去业务边界。

### 4. 判断是否需要单独拆原型任务

满足以下任一情况时，单独拆“原型任务”：

- 新增页面
- 现有页面结构变化明显
- 新增筛选区、列表区、统计卡片、汇总模块
- 存在多个状态，如空状态、加载状态、失败状态、无权限状态
- 产品、设计、研发对页面元素理解还不一致

如果只是“在现有页面加一两个字段”，通常不需要单独原型任务，可直接在前端任务里写明字段调整。

### 5. 把每个任务写成可执行状态

每个任务默认应包含：

- 任务类型
- 目标
- 范围
- 候选代码落点
- 前置依赖
- 预期产出
- 完成标志
- 风险或回归关注点

如果是原型任务，还要补：

- 页面名称和入口
- 使用角色
- 页面目标
- 页面区块结构
- 查询条件
- 列表字段 / 统计卡片 / 图表
- 操作按钮
- 详情页 / 弹窗 / 抽屉
- 空状态 / 加载状态 / 失败状态 / 无权限状态
- 权限差异
- 时间与金额口径
- 导出要求

任务颗粒度要让研发看完就能估时、知道从哪里下手，但也不要细到“改一行 SQL”这种微任务。

### 6. 输出正式任务拆分文档

默认输出到：

- `docs/requirements/{模块目录}/{功能名称}-任务拆分.md`

用户想要固定模板时，优先使用 [references/task-split-template.md](references/task-split-template.md)。

## 输出要求

输出要“实现感知”，但不要直接写成技术方案、接口定义或数据库设计，除非用户明确要这些内容。

重点写清楚：

- 要改什么
- 大概率改到哪里
- 哪些任务必须先做
- 做完后怎么验证
- 是否需要原型
- 是否涉及前端和后端协同

避免出现：

- “开发后端接口”这类空泛任务
- 只是把 PRD 换个标题重复一遍
- 在没看仓库的情况下写出假精确结论

## 与代码及设计对齐

使用真实入口、服务、数据访问和测试位置说明任务的落点。仓库未包含相关客户端时，记录待核对的目标仓库和接口依赖。规则变更影响统计口径、展示或历史生效时，把相应验证放到可交付的业务任务中。按当前代码能确认的粒度写，尚无证据的目录和方法标为待定位。

## 输出前自检

输出前确认：

- 研发是否可以不反复翻 PRD 就直接开始任务 1
- 任务之间是否有清晰依赖关系
- 统计与展示改动是否被单独识别
- 测试与回归是否有明确任务承接
- 历史兼容与上线切换是否没有被遗漏
- 页面需求是否明确是否需要原型任务
- 每个任务是否都标了任务类型
- 每个任务是否都指向真实存在的模块或文件，或明确说明对应仓库待确认

如果以上有任何一项做不到，就继续收敛任务拆分，不要急着定稿。

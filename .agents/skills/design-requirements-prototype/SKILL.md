# Design Requirements Prototype

把页面设计建立在真实代码、已确认需求和现有设计体系上，最终交付可点击、可评审、可追溯的需求原型，而不是脱离系统另起一个演示项目。

## 产物契约

沿用用户实例中的 `{模块}/{功能}/` 主题及以下逻辑路径：

```text
规格索引.md
需求文档.md
原型设计/
  {feature}-prototype.html
  README.md                  # 仅在需要说明原型入口与评审路径时创建
```

页面目录、画板、页面说明和关联在当前工作台的设计模型中统一维护：跨页路径放 `workspace.overview`，单页字段、状态、交互放 `page.description`。同页多状态可用 `descriptionPageId` 共用一份说明。没有画板时创建 `status: planned` 的待设计页，后续在同一 ID 补画板并改为 `designed`。不另建 `页面设计/` 文档、页面清单或独立页面模块；旧说明只从设计版本记录追溯。

按 [平台说明](../../../README.md) 和项目配置确认存储方式。MySQL 模式以平台保存版本为准，批量维护使用设计 CLI。文件模式以当前实例工作区为准，使用浏览器内的设计编辑能力。HTML 和图片等静态附件放在主题的 `原型设计/`。CLI 草稿是临时编辑副本。

在用户已选择的设计工具中继续工作。用户明确指定 Paper、Figma 或其他工具时，遵循其选择和适用工作区规则；本工作台原生设计使用 [references/workbench-cli.md](references/workbench-cli.md)，整页通过 HTML/CSS 制作后导入，局部按元素 ID 修改，浏览器负责视觉与交互验收。

只修改需求产物。除非用户明确要求进入代码实现并确认目标仓库，不修改正式前端、后端或移动端代码。

## 工作流

### 1. 建立工作区上下文

1. 完整阅读工作区根部适用的 `AGENTS.md`。
2. 从项目文档与服务配置确认需求资料目录、相关业务仓库及当前能力。
3. 定位需求主题，按当前存储方式读取 `规格索引.md`、`需求文档.md`、设计目录和页面说明、`接口契约.md` 和已有原型；本工作台文档通过 `/api/document?path=模块/功能` 读取，配套文档增加 `file=对应逻辑路径`；设计与页面说明使用 `design pull`。不要因本地没有 Markdown 就断言文档缺失。
4. 若用户提供当前页面、截图、原型 URL 或已打开页面，先捕获其可见状态并作为视觉基线。
5. 若需求仍存在会改变页面架构、角色边界或核心流程的未决项，先记录并讨论；不要把建议写成已确认结论。

### 2. 对照真实代码取证

使用 `rg` 或 `rg --files` 优先检索最接近的真实页面、路由、菜单、权限标识、接口调用、状态字段和可复用组件。

至少核对：

- Web 页面外壳、侧边栏、顶部栏、表格、筛选区、弹窗和抽屉。
- 运营端或移动端页面容器、卡片、列表、底部导航、图片上传和表单交互。
- 菜单权限、按钮权限、登录端、数据范围与服务端鉴权候选位置。
- 页面是否真实接入接口，还是硬编码 Mock、未注册页面、空文件或孤立原型。
- 现有业务对象关系、字段来源与存量兼容规则。

将结论分为“现有可复用”“需要改造”“尚未实现”“待确认”，不得把 Mock 或页面骨架描述成已实现能力。

#### 已有功能的增量设计

在已上线功能上增加能力时，以线上页面和实际接入的源码为基线，只做完成新功能必需的改动。开画前，按各端的真实入口梳理本次功能涉及的列表、详情、配置、记录和返回路径。对照现有页面及源码，明确每页要保留的布局、控件、状态、权限和操作，以及本次要调整的内容和新增位置。已有画板也按这份对照校准。用户办理原有业务时，应能按原入口、原权限和原操作流程得到相同结果。用户明确要求重设计或改变既有行为时，按其指定范围处理。

按用户需要判断的事选择增补位置。现有字段、明细或筛选能表达时就在原处补齐。新增对象的主键、状态或统计日期与原列表不同时，再考虑局部页签或独立视图。每处调整都应能对应本次功能需要，沿用现有页面壳、菜单、组件与信息密度。确需改变默认视图或指标口径时，先核对需求依据和影响范围，明确历史数据、统计及导出的承接方式。

分别检查普通入口和新功能专用入口。普通详情默认打开原有业务视图，新功能的深链接或状态画板定位到对应区域。原有数据和操作按原业务对象展示，新增内容放到对应区域，权限分别核对。

用户只要求修正页面时，按授权范围更新原型及必要附件。设计经验沉淀到 skill，业务文档更新以用户授权和实际业务口径变化为依据。页面展示最终交付形态，设计理由留在授权的说明中。

例如为知识库文章详情增加审核记录，从普通列表打开详情时仍先显示文章内容，从审核队列打开时可定位到审核记录。验证两个入口选中同一篇文章，返回列表后原筛选条件仍在。

### 3. 先收口页面模型

在写 H5 前先形成最小页面模型：

1. 角色及其目标。
2. 入口和菜单归属。
3. 主流程与关键分支。
4. 页面清单及各端职责。
5. 权限、数据范围、上下级或归属关系。
6. 空状态、无权限、失败、停用、历史兼容等边界状态。
7. In Scope 与 Out of Scope。

业务闭环复杂时，按授权范围更新设计总说明及对应页面说明；页面目录直接使用设计记录，不手工维护第二份清单。用户只要求看图或修正原型时，直接制作并验证页面，交付可访问的原型入口。

#### 整个功能的页面关系与增量说明

收到跨页面评审意见时，先按本次功能列出真实菜单入口、主体对象、列表/详情/页签/弹窗关系，区分沿用、增量、新增与合并。先确定内容由谁承接，再修改关联页面；不要把详情内的配置、记录、流水等局部内容顺手扩成新菜单，也不要因页面名称前缀虚构使用端分组。检查范围以当前授权功能为界，不扩展到整个产品。

同一流程的编辑、确认、保存中、失败、返回及重新进入使用一致的数据与对象。权限限制操作不等于限制为单个对象；列表提示按当前可见集合汇总，详情描述具体对象，组织级范围与单对象状态分开。多对象状态要覆盖部分受影响，不只画全部正常或全部异常。核验至少走通一条跨页路径，确认对象 ID、范围、权限、业务字段和已保存配置没有跳回默认值。

存量页面在工作台右侧提供简短的“本次页面改动”：原入口、沿用能力、本次新增或调整、所属页面/弹窗关系；无业务增量的沿用页也明确写清。已支持原生 `changeSummary` 时用 design CLI 维护；否则使用当前可用的页面说明能力。说明不写入最终业务页面，不把设计方法写成业务需求，也不为补说明擅自扩建编辑器。用户明确要求新增编辑器说明能力时再按其授权实施。合并或改版后重写为最终差异，避免只追加一串互相矛盾的修改记录。

### 4. 提取现有视觉基线

从当前代码或用户认可的页面中记录并复用：

- 主色、背景色、文字层级、边框色、圆角和阴影。
- 页面栅格、侧栏宽度、顶部栏高度、内容边距和表格密度。
- Element/Element Plus、UniApp 或项目自有组件的按钮、表单和反馈形式。
- 项目已有 iconfont、PNG、字体、Logo 和导航图标。

优先引用现有资源。不得用 emoji、ASCII、文本符号、手写 SVG、CSS 绘图或占位方块伪造可见图标。缺少关键视觉资产且无法从现有代码取得时，说明缺口并使用适用的图像生成能力；不要凭空换一套视觉语言。

### 5. 制作并维护页面原型

绘制存量页面时，以核对过的现有页面或画板为底稿，在对应位置增加字段、操作或页签。需要重新绘制时，先还原原布局、控件和交互，再加入本次新增内容。保留原筛选、列表操作和记录入口，沿用详情与编辑的打开方式和返回路径。空列表、只读等受影响的状态也按原有条件呈现控件和操作。完成后按[存量页面兼容验收](references/quality-gates.md#存量页面兼容验收)检查。

默认使用单文件 HTML 原型，只有复杂度确实需要时才拆分资源；静态附件放在需求主题的 `原型设计/`，不要初始化独立 React/Vue/Next 演示项目。

本工作台原生设计按 [references/workbench-cli.md](references/workbench-cli.md) 操作：

- 先 `pull` 当前画板、页面说明、元素说明和版本基线，再制作或编辑；整页用 `import`，多项修改用 `patch`，由一次 `apply` 原子保存。
- 修改已有画板优先从 `html` 导出保留元素 ID 的当前 HTML。局部文案和简单样式用 `elements` 定位后按 ID 修改，保留脚本、子元素和其他源码。
- 保持继续使用的画板 ID 和已有 `data-wb-element`。替换整页时检查元素说明、需求关联及流程到页面的引用；不能通过删说明或换 ID 掩盖断链。已淘汰画板按下述清理流程删除，不为保留 ID 维持重复页面。
- `source` 仅记录静态附件来源，画板保存的是 HTML 快照。编辑附件不会自动更新画板，改画板也不会自动回写附件；按实际交付范围显式同步，已淘汰附件与旧画板一起清理。
- 提交前检查差异和服务端 dry-run，提交后核对回读结果，再进入浏览器验收。画板与说明是共享在线数据，版本冲突时重新拉取合并，不改版本号强推。

原型必须满足：

- 沿用当前系统的页面壳、信息密度和交互形式。
- 顶部可增加“评审导航”，但明确其不属于正式业务页面。
- 使用 hash 或等价轻量路由组织多页面，例如 `#web/accounts`、`#mobile/my`。
- 提供真实可理解的 Mock 数据，并标明“演示数据，不代表已实现”。
- 让主导航、标签、筛选、弹窗、抽屉、步骤表单、权限开关和核心 CTA 可操作。
- 为需要评审的状态提供场景切换，例如默认权限、只读、扩展授权、空状态或异常状态。
- 多端共用同一业务规则，但分别遵循各端现有视觉和操作习惯。
- 使用相对路径引用仓库内现有资源，保证从需求目录或本地静态服务可预览。

#### 页面合并与旧稿清理

用户已确认合并、替代或删除页面时，在本次交付中完成旧稿清理。先核对旧页独有的字段、操作、异常与权限表现是否已由保留页面承接，再删除已淘汰的画板和源稿；不扩展到无关页面或仍有独立用途的资料。

同一页面的不同状态可通过场景参数或交互展示。确有必须并排评审的布局、操作或权限差异时保留必要状态画板，不把被替代的独立页全部改名为“详情 · 某状态”继续保留。

清理覆盖原生画板、页面说明所有者与共用引用、源原型列表、HTML 页面集合和相关跳转。只改名、隐藏菜单或移入归档目录不等于删除；用户要求删除时应实际移除对应产物。历史追溯沿用版本记录，用户明确要求保留对照稿时另按该范围处理。按 [CLI 的页面删除流程](references/workbench-cli.md#合并后删除淘汰页面) 迁移引用和有效说明，再验证页面目录与保留页面的业务路径。

#### 复杂规则与场景演练

涉及多条件判断、异步等待、共享业务规则或现状/方案比较时，读取 [规则表、覆盖检查与场景演练](../flow-workbench/references/decision-rules-and-rehearsal.md)，复用流程建模规则，不在原型内另写一套业务口径。场景选择应改变输入事实；步骤、按钮可用性和结果由相同规则推导，不能只切换硬编码结果页。评审所需时提供下一步、事件触发、重置及简短轨迹，能解释命中条件、结果去向和等待原因。评审控制放在业务界面之外或按需展开，不给普通业务页面强加规则表、演练面板或说明条。

已有 Apifox 枚举、用例或测试关联优先引用，并记录来源及版本；样例数据不自动代表完整允许值。原型使用演示数据，场景演练在原型内模拟业务结果。交付分别说明原型交互已验证、规则推演范围和真实业务测试证据；编辑器缺少自动检查/演练能力时，可人工推演并如实记录，不将技能规范描述成已实现的平台能力。

#### 表格、记录页与关联选择器默认规则

- 业务表格以一行一条核心数据为准。默认禁止在单元格主值下再堆第二行灰色说明文字；编码、版本、范围、原因等信息如确有必要，应拆成独立列、标签、悬浮说明或放入详情页/抽屉。
- 记录页必须优先展示用户真正要比较的原始数值和关键结果，不能只展示编号、状态和时间。例如审核记录应直接看到审核前后状态、结论、审核时间和审核人。
- 当业务目标是查看变化或历史对比时，列表中的业务对象名称应可点击进入历史数据；历史页或抽屉使用按时间排列的真实记录表，不用装饰性卡片代替数据。
- 页面保持简单直接：主表格是视觉重点，减少重复摘要卡、说明条、彩色标签和同义指标；只保留完成当前判断所需的筛选、一个主要操作和必要状态。
- 新增/编辑关联关系不能只展示已选标签或静态 Mock。必须提供可操作的搜索、勾选/移除、已选数量和禁选原因，并验证至少一次实际选择变化。

### 6. 明确权限表现

设计权限管理本身，或改动确实涉及账号类型、角色、菜单授予或数据范围模型时，完整阅读 [references/permission-system-mapping.md](references/permission-system-mapping.md)，按其方法建立可追溯权限台账，再设计权限页或全景页。

普通业务页只调整某个动作由谁操作时，遵循[小范围变更与统一方案复用](../prd-architect/SKILL.md#小范围变更与统一方案复用)，引用既有统一权限方案，在相关页面状态表现按钮显隐或可用性，并说明接口复用统一鉴权即可。不因此重建权限台账、扩成全景设计，或为模拟身份而改写整套原型。已覆盖的权限状态可复用；仅修改说明且页面行为未变时，不重跑全套浏览器验收。

将权限拆成菜单可见、动作可用、数据可见和登录端四层；页面中不得只体现前端隐藏。

设计时同时表达：

- 默认权限与可调整权限。
- 创建者或上级的可授予上限。
- 条件授权入口。
- 禁止、高危、只读和脱敏状态。
- 无权限时是隐藏、禁用还是提示申请。
- 存量账号或数据升级后的兼容表现。

不要让账户类型替代真实权限判定，也不要让“可查看某对象”自动推导出新增、编辑、删除、资金或授权能力。

### 7. 浏览器验证并迭代

完整阅读 [references/quality-gates.md](references/quality-gates.md)，按其中清单验收。

使用用户当前选择的浏览器打开保存后的工作台设计入口或本地静态 H5。CLI 结构校验和导出成功不能替代视觉与交互验收。按本次目标端及受影响范围验证：

- Web 页的目标桌面尺寸。
- 涉及移动端或响应式时的真实窄屏尺寸。
- 核心主流程从入口到完成。
- 场景切换和条件权限。
- 控制台错误、资源加载、横向溢出、截断、错位和点击失效。
- 参考页面与实现页面在相同尺寸、相近状态下的并排视觉差异。

发现问题后修正，再重复受影响的最小验证范围；不要以截图本身代替功能和结构验证。

### 8. 回填规格并交付

任务包含文档维护时，按当前存储方式更新需求主题的 `规格索引.md`。按项目现用方式更新以下内容。

- 更新日期和需求阶段。
- 增加原型入口与说明入口。
- 记录已确认页面、权限和端侧口径。
- 将尚未确认的产品决策继续保留为待确认项。
- 调整下一步为评审、接口契约或研发拆分。

交付时先给出可点击的工作台画板入口或本地原型文件，再简述覆盖页面、核心权限边界、保存与验证结果。原生画板可按需经 CLI 导出 PNG、JPG、PDF 或 HTML，导出本身不保存草稿。保持已验证页面在用户选择的浏览器中打开；仅在本次授权范围内发布或共享，不把保存本机工作台等同于另行部署。

## 决策边界

- 信息足以保持用户意图时，做最小合理假设并继续，在交付中说明。任务包含规格维护时同步记录。
- 缺少关键代码、参考页面或视觉来源时，先完成安全的只读取证；仍无法确定再向用户询问。
- 需要新增外部系统、真实账号、生产数据、线上发布或正式代码变更时，停止扩张范围并取得授权。
- 需求与当前实现冲突时，以当前源码作为现状证据，以已确认需求作为目标；分别记录，不混为一谈。

## 禁止事项

- 业务原型放在对应需求目录的 `原型设计/` 下。
- 不为一个需求另建独立演示项目。
- 不把前端隐藏等同于完整权限控制。
- 不为了“更好看”脱离现有设计体系重做视觉。
- 不用静态图片替代用户明确要求的可交互 H5。
- 不把未实现、Mock、空页面或孤立代码包装成现有能力。
- 不在用户未要求时发布、部署、提交或推送。

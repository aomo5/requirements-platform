# PRD Architect

将产品需求的原始输入（如老板口述、会议记录、聊天记录、零散想法、需求变更说明）整理成结构化、可评审、可继续拆页面与任务的正式 PRD 文档。

## 使用场景

- 用户提供了零散的需求描述，需要整理成规范文档
- 需要将口头沟通或会议记录转化为 PRD
- 需求文档需要补充结构，便于后续页面设计和开发
- 需求涉及多个端（如微信小程序、支付宝小程序、App、运营后台、管理后台），需要统一梳理
- 需求还不够完整，需要在整理过程中显式暴露待确认项
- 需求后续需要前后端接口对接时，先在 PRD 中写清业务口径和页面需要，再交给 `$interface-contract` 生成接口契约

## 不适用场景

- 用户要的是研发任务清单或实施排期
- 用户要的是页面字段清单或页面交互细化
- 用户要的是接口定义、数据库表结构、代码实现
- 用户只需要一句文案或按钮提示语
- 输入已经是一份完整 PRD，仅需轻微润色

## 交互模式

### 模式 1：需求澄清模式
当用户明显仍在讨论、探索、补充细节，或明确表示“先不要出正式文档”时：

- 先输出需求理解摘要
- 列出待确认项
- 列出关键分歧点
- 列出建议补充的信息
- 不直接生成完整 PRD
- 当存在多个未确认关键项时，优先停留在需求澄清模式，不要强行进入 PRD 生成模式。

### 模式 2：PRD 生成模式
当用户明确要求“整理成正式 PRD”“输出需求文档”“形成评审稿”时：

- 按完整 PRD 结构输出正式文档
- 如果信息不足，保留“待确认项”，不要强行补全

### 模式 3：现有需求维护模式
当用户补充、调整已有需求，或确认此前待定的规则时，读取最新正文，将变化合并到对应章节。保留有效内容和规则编号，按下方“现行版本与历史记录”维护，不重建一份并行 PRD。

## 核心原则

1. **先澄清目标，再罗列功能**

   优先识别业务背景、问题和目标，不要一上来堆功能点。

2. **保持产品视角，不写技术实现**

   重点描述“做什么、为什么做、做到什么程度”，而不是“怎么开发”。

3. **信息不足时优先列出待确认项**

   可以基于上下文做合理归纳，但不能把猜测写成已确认规则。

4. **输出应服务于后续设计和拆解**

   文档应便于继续做页面设计、流程评审、任务拆分和测试设计。

5. **多端需求必须区分端侧职责**

   不要把小程序、App、后台、服务端职责混写。

6. **异常、边界、权限、验收不可缺失**

   对业务规则、异常场景、权限边界和验收标准要重点补齐。

7. **优先结合项目全局认知**
   在当前仓库已启用 Repo Wiki 的情况下，优先参考项目现有模块、页面、流程、角色、规则和历史实现，避免脱离现有系统凭空设计需求文档。

## 设计资料承接

在当前需求工作台，页面目录、画板、说明和关联以设计模块为唯一当前来源。PRD 描述业务规则并引用设计入口，不复制另一套页面清单或单页规格；读取当前设计及页面说明后再核对业务口径。尚无画板时在设计中保留待设计页，旧页面文档与旧评审只供版本追溯。此规则不要求其他未使用该工作台的项目迁移工具。

## 小范围变更与统一方案复用

- 已有需求的小调整，先界定变化的业务规则及直接受影响的位置，只修改承载该规则、存在冲突或必须更新引用的内容。“检查关联一致性”不等于批量重写规格、接口、流程和整套原型；用户限定范围时遵守该边界。
- 账号权限、支付等已有或正在统一的方案优先复用。本需求确定业务结果与边界，引用统一方案；统一方案未完成时记录依赖，不自行写死数据库字段、方法或建立旁路实现。用户明确要求技术设计或发现真实能力缺口时，再按授权展开。
- 需求口径确认不自动升级为完整原型改造、跨页身份模拟或代码实现。按钮权限的小调整，只在直接相关状态体现显隐/可用性并补必要说明；不为演示一条规则批量改写无关页面脚本。
- 验证与变更相称：纯说明调整核对差异、引用和保存结果；有界面行为变化才检查受影响页面与路径，复用未变化的已通过证据。交付区分规则、说明、页面表现与实现改动，列出用户能看到差异的具体入口。

## 现行版本与历史记录

- 正文维护一份当前有效的完整方案。需求变化直接改写对应规则、范围、流程和验收标准，合并重复内容、移出失效结论；不要不断追加带日期的评审稿、补充说明或“以上方最新结论为准”。
- 待确认项得到结论后，归入对应正式规则及验收标准，并从待确认清单移除。清单只列仍未解决的问题，没有未决项就省略；尚待实施、真实配置或测试核验的事项另列交付待办，不继续称为业务待确认，也不把已确认写成已实现。
- 旧评审、原始输入、被替代方案和确认过程留在版本记录中，主文保留必要来源链接。清理前确认历史可回查；没有版本机制时先留可追溯快照。归档保留全文和证据，但不把历史原文、线上发布全文再附回当前正文。用户明确要求历史对比时另行提供。
- 同步检查本次受影响的规格索引、接口契约、流程及页面说明，使其采用同一现行规则；只改授权范围，外部发布沿用相应授权。保留稳定规则编号与有效关联，合并或移动段落后核验引用，避免正文整合导致页面、流程或验收关联失效。

## 输出原则

### 禁止输出
- 代码实现细节
- 接口定义（URL、参数、返回值）
- 数据库表结构
- 研发任务清单
- 具体技术选型建议

### 专注输出
- 背景与目标
- 用户角色和使用场景
- 范围与非范围
- 业务逻辑和规则
- 页面/模块功能清单
- 影响范围
- 核心流程
- 异常场景
- 验收标准
- 成功指标（如适用）
- 待确认项
- 风险与依赖

## 处理流程

### 0. 结合项目现状进行预分析

在 Repo Wiki 可用时，优先识别：
- 当前项目已有的相关模块
- 相似功能或历史实现
- 现有角色与权限模型
- 已有状态机、流程、页面结构
- 可能受影响的端和系统边界

先基于项目现状形成“现状理解摘要”，再进入正式 PRD 整理。

### 1. 提炼背景与目标

从用户输入中提取：

- **背景**：什么业务问题或机会触发了这个需求？为什么现在要做？
- **目标**：这个功能要达到什么效果？如何判断做成了？
- **成功标准**：如适用，补充成功指标或验证口径

### 2. 识别用户角色

列出所有相关角色：

- **主要用户**：直接使用功能的人
- **次要用户**：间接受影响的人
- **系统/后台角色**：管理员、运营人员、客服、财务等

如果是 B 端 / 平台类需求，要区分不同角色的职责和权限边界。

### 3. 梳理使用场景

为每个用户角色描述典型场景：

- 在什么情况下使用这个功能？
- 用户当前的痛点是什么？
- 使用后的预期改善是什么？
- 场景发生在哪个端、哪个页面、哪个流程阶段？

### 4. 定义需求范围

#### In Scope（范围内）
- 本次要实现的功能点
- 涉及的模块和页面
- 明确需要支持的端和角色

#### Out of Scope（范围外）
- 本次明确不处理的功能
- 明确延期到后续版本的内容
- 为避免误解需要显式排除的内容

### 5. 梳理业务规则

整理所有业务约束：

- 权限规则（谁能做什么）
- 校验规则（输入限制、业务限制）
- 计算规则（费用计算、分润计算、积分计算等）
- 时效规则（有效期、超时处理等）
- 状态规则（状态切换条件、关闭条件、终止条件等）
- 异常处理规则（失败、重复提交、冲突、回滚等）

### 6. 列出页面 / 模块清单

按功能模块组织：

| 模块 | 页面/功能点 | 说明 |
|------|------------|------|
| XX管理 | XX列表页 | 展示、搜索、筛选 |
| XX管理 | XX详情页 | 查看详细信息 |
| XX管理 | XX编辑页 | 新增、编辑、保存 |

若输入尚不完整，也应给出建议页面 / 模块清单，供后续页面设计继续补充。

### 7. 识别影响范围

明确本次需求可能影响的端和模块：

- 微信小程序
- 支付宝小程序
- App
- 运营后台
- 管理后台
- 服务端
- 第三方系统 / 外部接口
- 配置项 / 权限项 / 数据统计口径

需要显式写出受影响的系统范围，便于后续任务拆分和回归测试。

### 8. 描述核心流程

优先用结构化步骤描述主流程。

仅在流程较复杂、分支较多时，再补充 Mermaid 流程图草案。

流程描述需要包含：

- 起点
- 关键步骤
- 条件分支
- 关键状态变化
- 流程结束条件

### 9. 识别异常场景

列出可能的异常情况：

- 网络异常
- 数据不存在
- 权限不足
- 业务状态不允许
- 并发冲突
- 重复操作
- 第三方依赖失败
- 配置缺失或数据口径异常

描述每种异常的触发条件和业务处理方式。

### 10. 定义验收标准

为每个功能点编写可测试的验收标准。

**格式优先使用：**
- Given（前置条件）
- When（用户操作）
- Then（预期结果）

**要求：**
- 可观察
- 无歧义
- 可测试
- 尽量面向业务结果，而非技术实现结果

### 11. 列出待确认项

只记录当前仍需进一步确认的问题；已确认事项按“现行版本与历史记录”归入正文：

- 业务规则不明确的地方
- 需要产品 / 业务方决策的事项
- 依赖外部系统或第三方能力的确认项
- 跨部门协作尚未明确的事项

如果信息不足，不要强行补全，统一进入待确认项。

### 12. 识别风险与依赖

评估潜在风险：

- 业务风险（规则变更、合规、收费争议等）
- 协作风险（跨部门确认、外部依赖）
- 进度风险（资源不足、前置依赖未完成）
- 上线风险（影响老流程、影响老数据、回归范围大）

## 写作要求

1. **保持业务视角**：不要陷入技术实现细节
2. **适度抽象**：描述“做什么”，而非“怎么做”
3. **完整性检查**：确保关键功能点具备验收标准
4. **术语统一**：同一对象不要多种叫法混用
5. **避免空泛表述**：如“优化体验”“提升效率”必须展开成具体表现
6. **多端区分清晰**：不同端职责不要混写
7. **可追溯性**：业务规则要能对应到具体功能点或场景

## 输出前自检

输出前检查以下内容是否齐全：

* 是否写清楚了背景与目标
* 是否区分了范围内和范围外
* 是否明确了角色与场景
* 是否整理了关键业务规则
* 是否列出了页面 / 模块清单
* 是否写了影响范围
* 是否覆盖了核心流程
* 是否列出了异常场景
* 是否有可测试的验收标准
* 待确认项是否仅含真实未决问题，已确认结论是否已归入正式规则
* 正文是否只有一套现行口径，旧评审是否可从版本记录追溯，关联文档及引用是否一致
* 是否识别了风险与依赖
* 是否避免写入技术实现细节

## 保存与后续衔接

沿用项目已有的模块、主题路径和需求编号。需求平台中的主文档使用 `需求文档.md`，`规格索引.md` 记录状态、有效入口和真正未决的问题。MySQL 模式通过 [workbench-cli](../workbench-cli/SKILL.md) 保存当前版本，历史放版本记录。文件模式按用户实例的资料目录维护 Markdown。需要模板时参考 [PRD 模板](references/prd-template.md)。

后续按改动范围使用 [流程](../flow-workbench/SKILL.md)、[设计原型](../design-requirements-prototype/SKILL.md)、[接口契约](../interface-contract/SKILL.md) 或 [任务拆分](../task-splitter/SKILL.md)。使用现有主题与关联，避免拆出另一份当前需求。
